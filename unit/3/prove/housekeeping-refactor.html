Refatorando e Otimizando Sua Aplicação Express

Nesta tarefa, você refatorará sua aplicação Express para melhorar sua organização, desempenho e manutenibilidade. Você implementará um sistema dinâmico de carregamento de ativos que permite que as páginas carreguem apenas o CSS e o JavaScript de que precisam, e reorganizará seus arquivos de visualização para seguir padrões MVC consistentes.

A refatoração é o processo de reestruturar o código existente sem alterar seu comportamento externo. Esta tarefa se concentra em eliminar ineficiências e aplicar as melhores práticas que tornarão sua aplicação mais escalável e mais fácil de manter à medida que cresce.

Entendendo os Problemas que Precisamos Resolver

Sua aplicação atual tem vários problemas organizacionais e de desempenho. O problema mais significativo é o carregamento ineficiente de ativos. Atualmente, seu partial de cabeçalho carrega arquivos CSS para cada seção do seu site em todas as páginas. Isso significa que a página inicial carrega estilos de catálogo que não usa, as páginas de catálogo carregam estilos de corpo docente que não precisam e assim por diante. À medida que sua aplicação cresce e você adiciona mais seções, esse problema se agrava: cada página carrega CSS para cada seção, independentemente de precisar ou não desses estilos.

Essa abordagem desperdiça largura de banda, reduz a velocidade do carregamento das páginas e viola o DRY (Don't Repeat Yourself) princípio. Quando você precisa adicionar ou modificar estilos específicos de uma seção, precisa atualizar vários arquivos e se lembrar de quais páginas precisam de quais folhas de estilo. Uma abordagem melhor carregaria estilos dinamicamente com base em qual rota está sendo acessada.

O segundo problema é a organização inconsistente de visualizações. Sua seção de corpo docente tem suas visualizações organizadas em um subdiretório dedicado (src/views/faculty/), mas suas visualizações de catálogo estão espalhadas na pasta principal de visualizações. Essa inconsistência torna a base de código mais difícil de navegar e quebra o agrupamento lógico que os padrões MVC incentivam. Todas as visualizações relacionadas de uma seção devem ser organizadas juntas.

Por fim, há uma inconsistência de nomenclatura em suas visualizações de catálogo. A visualização de detalhes está atualmente nomeada course-detail.ejs, mas como você está trabalhando com um sistema de catálogo, ela deveria ser nomeada catalog-detail.ejs para corresponder à seção à qual pertence. Quando as visualizações forem movidas para seus subdiretórios adequados, essa nomenclatura se tornará catalog/detail.ejs, o que é tanto mais limpo quanto mais fácil de manter.

Instruções da Tarefa

1. Estender o Middleware Global com Gerenciamento de Ativos

Sua aplicação possui atualmente um middleware global em src/middleware/global.js que adiciona variáveis locais a todos os modelos. Você estenderá esse middleware adicionando funcionalidade de gerenciamento de ativos que permite que as rotas adicionem dinamicamente arquivos CSS e JavaScript conforme necessário.

Primeiro, examine sua estrutura atual de middleware. Abra src/middleware/global.js para ver a função addLocalVariables existente. Esse middleware é executado para cada requisição e configura variáveis como currentYear, greeting, e bodyClass que todos os seus modelos podem acessar.

Você adicionará uma nova função auxiliar chamada setHeadAssetsFunctionality que cria métodos para gerenciar ativos de CSS e JavaScript. Adicione essa função ao seu global.js arquivo, colocando-a antes da função addLocalVariables: 


        /**
         * Express middleware that adds head asset management functionality to routes.
         * Provides arrays for storing CSS and JS assets with priority support.
         * 
         * Adds these methods to the response object:
         * - res.addStyle(css, priority) - Add CSS/link tags to head
         * - res.addScript(js, priority) - Add script tags 
         * 
         * Adds these functions to EJS templates via res.locals:
         * - renderStyles() - Outputs all CSS in priority order (high to low)
         * - renderScripts() - Outputs all JS in priority order (high to low)
         */
        const setHeadAssetsFunctionality = (res) => {
            res.locals.styles = [];
            res.locals.scripts = [];
            
            res.addStyle = (css, priority = 0) => {
                res.locals.styles.push({ content: css, priority });
            };
            
            res.addScript = (js, priority = 0) => {
                res.locals.scripts.push({ content: js, priority });
            };
            
            // These functions will be available in EJS templates
            res.locals.renderStyles = () => {
                return res.locals.styles
                    // Sort by priority: higher numbers load first
                    .sort((a, b) => b.priority - a.priority)
                    .map(item => item.content)
                    .join('\n');
            };
            
            res.locals.renderScripts = () => {
                return res.locals.scripts
                    // Sort by priority: higher numbers load first
                    .sort((a, b) => b.priority - a.priority)
                    .map(item => item.content)
                    .join('\n');
            };
        };

Agora integre essa funcionalidade ao seu middleware addLocalVariables existente. Dentro da função addLocalVariables, adicione uma chamada para setHeadAssetsFunctionality(res) antes da chamada de next(). Isso garante que cada requisição tenha acesso aos métodos de gerenciamento de ativos.

  • O setHeadAssetsFunctionality auxiliar:
    • Cria res.locals.styles e res.locals.scripts arrays para armazenar ativos.
    • Adiciona métodos de resposta:
      • res.addStyle(css, priority)
      • res.addScript(js, priority)
    • Expõe os assistentes de modelo via res.locals:
      • renderStyles() — exibe o CSS ordenado por prioridade (alta → baixa).
      • renderScripts() — exibe o JS ordenado por prioridade (alta → baixa).
  • A prioridade controla a ordem de carregamento quando múltiplos assets são registrados: números maiores são emitidos primeiro para que arquivos de menor prioridade possam sobrescrevê-los.

2. Implemente o Carregamento Dinâmico de Assets no Cabeçalho

Agora que seu middleware fornece funcionalidade de gerenciamento de assets, você precisa atualizar seu partial de cabeçalho para usá-lo. Atualmente, seu src/views/partials/header.ejs arquivo carrega todos os arquivos CSS diretamente, incluindo estilos específicos de seção que não são necessários em todas as páginas.

Abra src/views/partials/header.ejs e localize estas linhas na seção <head>: 


        <link rel="stylesheet" href="/css/catalog.css">
        <link rel="stylesheet" href="/css/faculty.css">

Remova estas linhas completamente. Em seguida, no mesmo local onde esses links estavam, adicione as funções de renderização dinâmica: 


        <%- renderStyles() %>
        <%- renderScripts() %>

Essas funções exibirão quaisquer assets CSS e JavaScript que foram registrados por rotas usando res.addStyle() e res.addScript(). Neste ponto, salve suas alterações e teste sua aplicação. Você notará que as páginas de catálogo e corpo docente não possuem mais seus estilos específicos de seção. Este é o comportamento esperado, já que você removeu o carregamento global, mas ainda não adicionou o carregamento específico de rota. Você corrigirá isso na próxima etapa.

3. Adicione Middleware em Nível de Roteador para Estilos Específicos de Seção

Em vez de adicionar estilos manualmente em cada manipulador de rota, você usará middleware em nível de roteador para carregar automaticamente o CSS específico de seção para todas as rotas em um determinado caminho. Essa abordagem é mais fácil de manter e segue o princípio DRY: você define o carregamento de assets uma vez, e ele se aplica a todas as rotas correspondentes.

O middleware em nível de roteador é executado após o middleware global, mas antes dos manipuladores de rota individuais. Ao registrar o middleware para padrões como /catalog/*, você pode adicionar automaticamente estilos para todas as rotas de catálogo sem modificar cada manipulador de rota. Esse padrão é especialmente poderoso à medida que sua aplicação cresce: adicionar uma nova rota de catálogo inclui automaticamente os estilos de catálogo sem nenhum código adicional.

Ordem de Execução do Middleware

O Express processa requisições por meio de uma cadeia: o middleware global (em server.js) é executado primeiro, depois o middleware em nível de roteador (em routes.js) para rotas correspondentes, e finalmente os manipuladores de rota individuais. Essa ordem garante que o res.addStyle() esteja disponível quando o middleware do seu roteador for executado, já que o middleware global configurou essa funcionalidade.

Abra o seu arquivo src/controllers/routes.js. Este arquivo define todas as rotas da sua aplicação usando o Express Router. Atualmente, ele importa controladores e registra rotas, mas não possui nenhum middleware em nível de roteador. Você precisa examinar a estrutura para entender onde adicionar o middleware.

Perto do topo do arquivo, você deve ver o roteador sendo criado e algumas importações: 


        import { Router } from 'express';
        import { homePage } from './home.js';
        import { aboutPage } from './about.js';
        // ... other imports

        const router = Router();

        // Router middleware should be added here, before route definitions

        // Route definitions
        router.get('/', homePage);
        router.get('/about', aboutPage);
        router.get('/catalog', catalogPage);
        router.get('/catalog/:slugId', courseDetailPage);
        // ... other routes

        export default router;

O middleware do roteador deve ser registrado após a criação do roteador, mas antes das definições de rota. Se o middleware for registrado após as rotas, ele não será executado para essas rotas. Adicione este middleware após as importações, mas antes das definições de rota: 


        // Add catalog-specific styles to all catalog routes
        router.use('/catalog', (req, res, next) => {
            res.addStyle('<link rel="stylesheet" href="/css/catalog.css">');
            next();
        });

Este middleware usa o padrão /catalog, que corresponde a /catalog e a qualquer rota que comece com /catalog/ (como /catalog/:slugId). Quando uma rota correspondente é acessada, o middleware roda, chama res.addStyle() para registrar o CSS do catálogo e, em seguida, chama next() para passar o controle para o manipulador de rota. O CSS registrado será exibido quando o modelo chamar renderStyles().

Salve suas alterações e teste suas páginas de catálogo. A estilização do catálogo agora deve estar restaurada. No entanto, suas páginas de corpo docente ainda carecem de estilização. Aplique o mesmo padrão para as rotas de corpo docente adicionando um middleware semelhante para o padrão /faculty. Use o middleware de catálogo como referência, mas registre faculty.css em seu lugar.

Versões mais antigas do Express e de outros frameworks semelhantes ao Express costumam usar o caractere curinga asterisco (*) em padrões de middleware de roteador (por exemplo, /catalog/*). No Express moderno, usar apenas o caminho base (por exemplo, /catalog) é suficiente para corresponder a todas as subrotas. Por razões de segurança e desempenho, curingas não são mais permitidos em definições de rota do Express.

4. Reorganize os Arquivos de Visualização do Catálogo

Suas visualizações de corpo docente estão organizadas em um subdiretório dedicado (src/views/faculty/) com arquivos chamados list.ejs e detail.ejs. Suas visualizações de catálogo devem seguir o mesmo padrão por consistência. Organizar as visualizações por seção torna a base de código mais fácil de navegar e se alinha aos princípios do MVC, que agrupam arquivos relacionados.

Crie um novo diretório em src/views/catalog/. Em seguida, mova e renomeie os arquivos de visualização do seu catálogo:

  • Mova src/views/catalog.ejs para src/views/catalog/list.ejs
  • Mova src/views/course-detail.ejs para src/views/catalog/detail.ejs

Após a reorganização, a estrutura do seu diretório de visualizações deve ser parecida com esta: 


        [project-root]
        └── src/
            └── views/
                ├── catalog/
                │   ├── detail.ejs
                │   └── list.ejs
                ├── faculty/
                │   ├── detail.ejs
                │   └── list.ejs
                ├── partials/
                │   ├── footer.ejs
                │   └── header.ejs
                ├── about.ejs
                ├── demo.ejs
                └── home.ejs

5. Corrigir os caminhos de inclusão de parciais

Mover os arquivos de visualização do catálogo para um subdiretório altera o caminho relativo para seus parciais. Os parciais de cabeçalho e rodapé estão em src/views/partials/, mas suas visualizações do catálogo agora estão em src/views/catalog/, que está um nível mais profundo.

Abra ambos src/views/catalog/list.ejs e src/views/catalog/detail.ejs. Encontre as instruções de inclusão parcial no topo e na parte inferior de cada arquivo: 


        <%- include('partials/header') %>
        ...
        <%- include('partials/footer') %>

Atualize esses caminhos para usar ../ para navegar um nível acima no diretório: 


        <%- include('../partials/header') %>
        ...
        <%- include('../partials/footer') %>

O ../ prefixo diz ao EJS para procurar no diretório pai (views) em vez do diretório atual (catalog). Isso permite que as inclusões encontrem os parciais em views/partials/.

6. Atualizar as referências do controlador

Após mover os arquivos de visualização, você precisa atualizar seu controlador de catálogo para referenciar os novos caminhos de visualização. Abra src/controllers/catalog/catalog.js e encontre todas as chamadas res.render().

Atualize os nomes das visualizações para corresponder às novas localizações de arquivos:

  • Altere res.render('catalog', ...) para res.render('catalog/list', ...)
  • Altere res.render('course-detail', ...) para res.render('catalog/detail', ...)

O caminho da visualização catalog/list diz ao Express para procurar por list.ejs dentro do subdiretório catalog da sua pasta de visualizações. Salve suas alterações e teste todas as rotas do catálogo para verificar se as visualizações são renderizadas corretamente e os estilos são carregados adequadamente.

Resumo dos Conceitos Chave

Esta Tarefa de refatoração introduziu vários padrões importantes para a construção de aplicações web de fácil manutenção. O sistema dinâmico de carregamento de recursos que você implementou permite que as rotas carreguem seletivamente apenas o CSS e o JavaScript necessários, em vez de carregar tudo globalmente. Isso melhora o desempenho ao reduzir o uso desnecessário de largura de banda e os tempos de carregamento de página.

O padrão de middleware no nível do roteador é particularmente poderoso. Em vez de repetir o código de carregamento de recursos em cada manipulador de rota, você define o middleware uma vez para um padrão de rota e ele se aplica automaticamente a todas as rotas correspondentes. Isso segue o princípio DRY e torna seu código mais fácil de manter: quando precisar adicionar uma nova folha de estilo a uma seção, você a altera em um único lugar, em vez de procurar em vários manipuladores de rotas.

O middleware em nível de roteador fica entre o middleware global e os manipuladores de rotas na cadeia de middleware do Express. O middleware global é executado para cada requisição, o middleware de roteador é executado para rotas que correspondem a padrões específicos e os manipuladores de rotas contêm a lógica de negócios para rotas individuais. Entender essa ordem de execução ajuda você a decidir onde colocar diferentes tipos de funcionalidade: preocupações verdadeiramente globais vão para o middleware global, preocupações específicas de uma seção vão para o middleware do roteador e a lógica específica da rota fica nos manipuladores.

Ao reorganizar seus arquivos de visualização em subdiretórios, você tornou a estrutura da sua aplicação mais consistente e fácil de navegar. Esse padrão de organização escala bem: conforme você adiciona mais seções à sua aplicação, cada seção recebe sua própria pasta de visualizações, sua própria pasta de controladores e seu próprio middleware de roteador para preocupações específicas da seção. Essa abordagem modular torna as grandes aplicações gerenciáveis.

Experimente e Estenda

Agora que você tem o carregamento dinâmico de recursos funcionando, experimente o sistema de prioridades. Tente adicionar vários arquivos CSS a uma rota com diferentes valores de prioridade para ver como eles são carregados em ordem. Lembre-se de que números de prioridade mais altos são carregados primeiro, o que significa que estilos com prioridade mais baixa podem sobrescrevê-los.

Considere adicionar arquivos JavaScript específicos de página usando o mesmo padrão. Crie um arquivo JavaScript simples no seu diretório público e use res.addScript() em um manipulador de rota para carregá-lo apenas em páginas específicas. Posicione a chamada renderScripts() na parte inferior do seu layout, logo antes da tag de fechamento </body>, para garantir que os scripts sejam carregados após o conteúdo da página.

Pense em outros usos para middlewares em nível de roteador além do carregamento de recursos. Esse padrão funciona bem para qualquer funcionalidade que se aplique a todas as rotas em uma seção: registrar o acesso às rotas em log, verificar o status da autenticação, carregar dados específicos de uma seção ou definir variáveis de modelo comuns. Sempre que se pegar repetindo código em vários manipuladores de rota, considere se o middleware de roteador poderia eliminar essa duplicação.

Solução de problemas

Se o seu middleware não parece estar em execução, verifique se ele foi registrado antes das definições de rota em routes.js. O middleware registrado após as rotas não afetará essas rotas. A ordem deve ser: criar o roteador, registrar o middleware, definir as rotas.

Se os arquivos CSS não estiverem carregando nas páginas do catálogo ou do corpo docente, verifique se você adicionou a renderStyles() chamada para o seu partial de cabeçalho e que você removeu as antigas <link> tags codificadas diretamente. Também verifique se o middleware do seu roteador está chamando res.addStyle() com o caminho de arquivo correto e chamando next() para passar o controle para o manipulador de rota.

Se você vir erros sobre exibições não serem encontradas após a reorganização, verifique novamente os caminhos nas chamadas de renderização do seu controlador. O caminho catalog/list deve corresponder à localização do arquivo src/views/catalog/list.ejs. Também verifique se as inclusões de partials nas exibições do catálogo usam ../partials/header em vez de partials/header já que as exibições agora estão em um subdiretório.

Se o padrão de middleware do roteador /catalog/* não corresponder às suas rotas, verifique se as definições de rota usam caminhos como /catalog e /catalog/:slugId. O caractere curinga asterisco corresponde ao caminho base e a quaisquer subcaminhos, portanto ambos devem funcionar. Se você ainda estiver tendo problemas, tente usar apenas /catalog sem o asterisco, embora isso exija um middleware separado para a rota de detalhes.
