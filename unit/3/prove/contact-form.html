Construindo seu Primeiro Formulário: Fale Conosco

Nesta tarefa, você criará um formulário de contato funcional que permite aos usuários enviar mensagens por meio do seu site. Este formulário demonstrará o ciclo completo do processamento de formulários web: exibir um formulário aos usuários, manipular seus envios com requisições POST, validar os dados tanto do lado do cliente quanto do servidor e armazenar os resultados em seu banco de dados PostgreSQL.

Você construirá esta funcionalidade usando a arquitetura MVC adequada, criando controladores dedicados para manipulação de formulários, modelos para operações de banco de dados e exibições para interação do usuário. Esta tarefa introduz a validação do lado do servidor usando a biblioteca express-validator, que fornece ferramentas de validação de nível profissional usadas em aplicações web em produção.

Entendendo o Problema

Sites estáticos só podem exibir informações, mas aplicações web dinâmicas precisam coletar e processar a entrada do usuário. Formulários de contato são uma das maneiras mais comuns pelas quais os sites interagem com seus visitantes, permitindo que os usuários façam perguntas, relatem problemas ou forneçam feedback sem a necessidade de clientes de e-mail ou serviços externos.

No entanto, aceitar a entrada do usuário cria vários desafios que os sites estáticos nunca enfrentam. Os usuários podem enviar formulários vazios, fornecer dados inválidos ou até mesmo tentar injetar conteúdo malicioso. Sua aplicação precisa validar todos os dados recebidos, tratar erros de forma harmoniosa e armazenar os envios válidos com segurança em seu banco de dados.

Esta tarefa aborda esses desafios implementando tanto a validação do lado do cliente (para feedback imediato do usuário) quanto a validação do lado do servidor (para segurança e integridade dos dados). Você criará uma tabela no banco de dados para armazenar envios, construirá rotas e controladores para manipular o processamento do formulário e implementará uma validação abrangente para garantir a qualidade dos dados.

Preparação

Antes de construir o formulário de contato, você precisa criar uma tabela no banco de dados para armazenar os envios do formulário de contato. Você usará uma abordagem de arquivo SQL que segue o mesmo padrão do seu seed.sql arquivo existente, mas em um arquivo separado dedicado às suas tarefas de prática.

Crie um novo arquivo em src/models/sql/practice.sql. Este arquivo servirá como um espaço dedicado para todas as alterações no banco de dados das suas tarefas de prática ao longo do curso. Você adicionará a tabela do formulário de contato agora, e tarefas futuras poderão adicionar tabelas adicionais ou modificações a este mesmo arquivo. Adicione o seguinte conteúdo: 


        -- Practice database tables for assignments
        -- This file accumulates changes from multiple assignments
        -- Add new tables and modifications here as you work through the course

        -- Contact form table
        CREATE TABLE IF NOT EXISTS contact_form (
            id SERIAL PRIMARY KEY,
            subject VARCHAR(255) NOT NULL,
            message TEXT NOT NULL,
            submitted TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );

Em seguida, modifique seu src/models/setup.js arquivo para executar este arquivo SQL de prática como parte do processo de semeadura. Abra setup.js e localize a linha que diz console.log('Database seeded successfully');. Imediatamente ANTES desta linha (após o await db.query(seedSQL); mas antes do log de sucesso), adicione o seguinte código: 


        // Run practice.sql if it exists (for student assignments)
        const practicePath = join(__dirname, 'sql', 'practice.sql');
        if (fs.existsSync(practicePath)) {
            const practiceSQL = fs.readFileSync(practicePath, 'utf8');
            await db.query(practiceSQL);
            console.log('Practice database tables initialized');
        }

Este código verifica se practice.sql existe e o executa como parte do processo de semeadura (seed). A verificação do arquivo garante que sua aplicação ainda funcione mesmo que você ainda não tenha criado o arquivo de prática. Este SQL de prática será executado toda vez que você disparar uma nova semeadura do banco de dados ao excluir dados da tabela faculty.

Entendendo a Abordagem com Arquivo SQL

Você pode se perguntar por que usamos um arquivo practice.sql separado em vez de colocar tudo em seed.sql. Esta separação mantém suas tarefas de prática isoladas da estrutura principal do banco de dados do curso. O seed.sql arquivo contém os dados iniciais que todo aluno precisa, enquanto o practice.sql contém seu trabalho de prática individual que crescerá ao longo do tempo.

Observe o uso de CREATE TABLE IF NOT EXISTS no SQL. Isso torna o script idempotente, o que significa que você pode executá-lo várias vezes com segurança, sem erros. Toda vez que o processo de semeadura for executado (quando a tabela faculty estiver vazia), ele também executará o seu SQL de prática. A IF NOT EXISTS cláusula previne erros se a tabela já existir.

Reinicie seu servidor e verifique se a tabela foi criada checando o console do seu servidor. Você deve ver a mensagem "Practice database tables initialized" após "Database seeded successfully". Use o pgAdmin para examinar as tabelas do seu banco de dados e confirmar que uma nova contact_form tabela existe com colunas para ID, subject, message e timestamp de envio (submitted). Não prossiga até confirmar que a tabela existe e que seu servidor inicia sem erros.

Lembre-se de que, para semear novamente o banco de dados e executar o SQL de prática novamente, você precisa excluir todos os dados da tabela faculty. Isso dispara o processo de semeadura, que agora inclui o seu arquivo SQL de prática.

Instruções da Tarefa

1. Instalar o Express-Validator

Instale a biblioteca express-validator, que fornece ferramentas de validação de nível profissional para aplicações Express: 


        pnpm install express-validator
Por que Usar uma Biblioteca de Validação?

Você pode se perguntar por que usamos o express-validator em vez de escrever nossas próprias funções de validação. Isso se conecta a um princípio importante mencionado anteriormente no curso: seja intencional sobre as dependências. Embora você possa escrever código de validação personalizado, usar o express-validator oferece vários benefícios importantes que justificam adicionar essa dependência:

Segurança: O express-validator é testado na prática por milhares de desenvolvedores e lida com casos limite de segurança (como prevenção de XSS e higienização adequada de entrada) que são fáceis de passar despercebidos em código personalizado. Escrever uma validação segura do zero exige um conhecimento profundo de vetores de ataque que a maioria dos desenvolvedores adquire apenas após anos de experiência.

Boas Práticas: Ele implementa padrões de validação de nível industrial usados em aplicações em produção, ensinando como desenvolvedores profissionais lidam com a validação. Quando você se juntar a uma equipe de desenvolvimento, quase certamente encontrará esta ou uma biblioteca de validação semelhante.

Menos Código, Menos Bugs: Escrever uma validação robusta do zero requer lidar com muitos casos limite. O express-validator fornece essa funcionalidade de forma pronta para uso, reduzindo bugs e economizando um tempo significativo de desenvolvimento. A alternativa seriam centenas de linhas de código de validação personalizado que precisariam de testes minuciosos.

Rico em Funcionalidades: Ele inclui validadores integrados para casos comuns (e-mail, URL, comprimento, padrões) que exigiriam uma quantidade significativa de código personalizado para serem replicados adequadamente. Esses validadores lidam com caracteres internacionais, vários formatos e casos limite que são fáceis de ignorar.

No desenvolvimento profissional, você quase sempre usará bibliotecas de validação em vez de escrever uma validação personalizada para cada projeto. Aprender o express-validator agora prepara você para práticas de desenvolvimento do mundo real e ensina quando adicionar uma dependência é a escolha certa.

2. Configurar o Express para Lidar com Requisições POST

Ganta que sua aplicação Express esteja configurada para analisar dados de formulário codificados em URL de requisições POST. Abra o seu server.js e adicione o seguinte middleware na seção onde você configura os middlewares do Express, logo após o código que serve arquivos estáticos: 


        // Allow Express to receive and process POST data
        app.use(express.urlencoded({ extended: true }));
        app.use(express.json());

A primeira linha habilita a análise de dados de formulário enviados com o tipo de conteúdo application/x-www-form-urlencoded, o qual é o que os formulários HTML usam por padrão. A segunda linha habilita a análise de dados JSON, o que será útil para futuras tarefas envolvendo APIs.

Esta configuração de middleware lida com dados de formulário baseados em texto e JSON, mas não lida com envios de arquivos. O envio de arquivos requer um middleware diferente que processa multipart/form-data, o qual é coberto em uma tarefa opcional mais adiante no curso. Para esta tarefa de formulário de contato, você trabalhará apenas com entrada de texto.

4. Configurar o Carregamento Dinâmico de CSS

Adicione o middleware à sua configuração de rotas para carregar o CSS do formulário de contato apenas em páginas relacionadas a contato. Abra src/controllers/routes.js e adicione o seguinte middleware com seus outros middlewares específicos de rota (perto do middleware de catálogo e corpo docente): 


        // Add contact-specific styles to all contact routes
        router.use('/contact', (req, res, next) => {
            res.addStyle('<link rel="stylesheet" href="/css/contact.css">');
            next();
        });

Isso garante que o arquivo CSS de contato seja carregado para qualquer rota que comece com /contact, seguindo o mesmo padrão que você implementou na tarefa de Refatoração de Organização.

5. Criar o Controlador de Contato

Crie o arquivo de controlador para a funcionalidade do seu formulário de contato. Crie src/controllers/forms/contact.js. Você pode notar que este arquivo conterá funções de controlador, regras de validação e definições de rota, tudo junto em um único arquivo. Este é um padrão comum e prático em aplicações Express para funcionalidades deste tamanho.

Compreendendo a Organização de Controllers

Em frameworks maiores, como Ruby on Rails ou ASP.NET MVC, controllers, rotas e validação costumam ser separados em arquivos ou camadas diferentes. No entanto, o Express é um framework minimalista que oferece flexibilidade na organização do código. Para funcionalidades de pequeno a médio porte, combinar funcionalidades relacionadas em um único arquivo de controller é uma abordagem padrão e prática.

Você pode perguntar: "Isso não viola a separação do MVC?" De forma alguma. A separação do MVC significa manter suas responsabilidades organizadas: os Models lidam com dados e operações de banco de dados, as Views lidam com a apresentação e os Controllers lidam com o processamento de requisição, validação e coordenação entre models e views. A validação e o roteamento fazem parte da camada do controller, não são responsabilidades separadas. O que importa é que a lógica do seu banco de dados permaneça nos models e a lógica de apresentação permaneça nas views.

Esta abordagem de arquivo único mantém toda a lógica do formulário de contato em um só lugar, tornando-a mais fácil de entender e manter. Você pode ver as regras de validação logo ao lado das funções do controller que as utilizam, e as rotas que conectam tudo. Conforme sua aplicação cresce, você pode dividir os arquivos se um controller ficar muito grande ou se as regras de validação precisarem ser reutilizadas em vários controllers. Por enquanto, manter o código relacionado junto segue o princípio de alta coesão e torna sua base de código mais fácil de manter.

Adicione o seguinte conteúdo a src/controllers/forms/contact.js: 


        import { Router } from 'express';
        import { body, validationResult } from 'express-validator';
        import { createContactForm, getAllContactForms } from '../../models/forms/contact.js';

        const router = Router();

        /**
         * Display the contact form page.
         */
        const showContactForm = (req, res) => {
            res.render('forms/contact/form', {
                title: 'Contact Us'
            });
        };

        /**
         * Handle contact form submission with validation.
         * If validation passes, save to database and redirect.
         * If validation fails, log errors and redirect back to form.
         */
        const handleContactSubmission = async (req, res) => {
            // Check for validation errors
            const errors = validationResult(req);
            
            if (!errors.isEmpty()) {
                // Log validation errors for developer debugging
                console.error('Validation errors:', errors.array());
                // Redirect back to form without saving
                return res.redirect('/contact');
            }

            // Extract validated data
            const { subject, message } = req.body;

            try {
                // Save to database
                await createContactForm(subject, message);
                console.log('Contact form submitted successfully');
                // Redirect to responses page on success
                res.redirect('/contact/responses');
            } catch (error) {
                console.error('Error saving contact form:', error);
                res.redirect('/contact');
            }
        };

        /**
         * Display all contact form submissions.
         */
        const showContactResponses = async (req, res) => {
            let contactForms = [];
            
            try {
                contactForms = await getAllContactForms();
            } catch (error) {
                console.error('Error retrieving contact forms:', error);
            }

            res.render('forms/contact/responses', {
                title: 'Contact Form Submissions',
                contactForms
            });
        };

        /**
         * GET /contact - Display the contact form
         */
        router.get('/', showContactForm);

        /**
         * POST /contact - Handle contact form submission with validation
         */
        router.post('/',
            [
                body('subject')
                    .trim()
                    .isLength({ min: 2 })
                    .withMessage('Subject must be at least 2 characters'),
                body('message')
                    .trim()
                    .isLength({ min: 10 })
                    .withMessage('Message must be at least 10 characters')
            ],
            handleContactSubmission
        );

        /**
         * GET /contact/responses - Display all contact form submissions
         */
        router.get('/responses', showContactResponses);

        export default router;

Nesta Tarefa, os erros de validação são registrados no log do console para depuração do desenvolvedor, e o usuário é simplesmente redirecionado de volta para o formulário. Em uma Tarefa futura, você aprenderá como exibir mensagens de erro úteis para os usuários quando a validação falhar, proporcionando uma melhor experiência do usuário. Por enquanto, o foco está na implementação de validação segura no lado do servidor e na compreensão do fluxo de trabalho de validação.

Agora integre estas rotas ao seu arquivo de rotas principal. Abra src/controllers/routes.js, importe as rotas de contato no topo junto com suas outras importações: 


        import contactRoutes from './forms/contact.js';

Em seguida, adicione as rotas de contato ao seu roteador após as outras definições de rota: 


        // Contact form routes
        router.use('/contact', contactRoutes);

6. Crie o Model de Contato

Crie o arquivo de model que lida com as operações de banco de dados para os envios do formulário de contato. Crie src/models/forms/contact.js com o seguinte conteúdo: 


        import db from '../db.js';

        /**
         * Inserts a new contact form submission into the database.
         * 
         * @param {string} subject - The subject of the contact message
         * @param {string} message - The message content
         * @returns {Promise<Object>} The newly created contact form record
         */
        const createContactForm = async (subject, message) => {
            const query = `
                INSERT INTO contact_form (subject, message)
                VALUES ($1, $2)
                RETURNING *
            `;
            const result = await db.query(query, [subject, message]);
            return result.rows[0];
        };

        /**
         * Retrieves all contact form submissions, ordered by most recent first.
         * 
         * @returns {Promise<Array>} Array of contact form records
         */
        const getAllContactForms = async () => {
            const query = `
                SELECT id, subject, message, submitted
                FROM contact_form
                ORDER BY submitted DESC
            `;
            const result = await db.query(query);
            return result.rows;
        };

        export { createContactForm, getAllContactForms };
Consultas Parametrizadas para Segurança

Observe como o model usa consultas parametrizadas com $1 e $2 placeholders em vez de concatenar a entrada do usuário diretamente em strings SQL. Isso é crítico para evitar ataques de injeção de SQL, onde usuários mal-intencionados poderiam manipular seu banco de dados inserindo comandos SQL em campos de formulário.

O driver do PostgreSQL escapa e sanitiza automaticamente os valores que você passa no segundo argumento para db.query(), garantindo que a entrada do usuário seja tratada como dados em vez de código SQL executável. Nunca concatene a entrada do usuário em consultas SQL, mesmo que ache que a entrada é segura.

7. Compreendendo o express-validator

A biblioteca express-validator fornece funções middleware que validam os dados da requisição recebida. Em seu arquivo de controller, você definiu regras de validação como um array de funções middleware na definição da rota, antes da sua função de controller. Cada regra de validação é executada em sequência, verificando condições específicas sobre os dados enviados.

A body() função cria um validador para um campo específico no corpo da requisição. Você pode encadear métodos para especificar regras de validação:

  • trim() remove espaços em branco do início e do fim do valor
  • isLength({ min: 2 }) exige que o valor tenha pelo menos 2 caracteres
  • withMessage() fornece uma mensagem de erro personalizada se a validação falhar

Em sua função de controller, a validationResult(req) função coleta todos os erros de validação da requisição. Se errors.isEmpty() retornar false, a validação falhou e você não deve processar os dados. O errors.array() método retorna um array de objetos de erro que você pode registrar no log ou exibir para os usuários.

Esta separação de responsabilidades mantém suas regras de validação próximas das definições de rota, enquanto mantém suas funções de controller focadas em manipular os dados validados. O middleware de validação é executado antes da sua função de controller, garantindo que o seu controller receba apenas dados válidos.

Métodos de Validação Comuns

O express-validator fornece muitos métodos de validação nativos que você pode usar:

  • isEmail() valida endereços de e-mail
  • isURL() valida URLs
  • isNumeric() garante que o valor contenha apenas números
  • isLength({ min, max }) verifica o tamanho da string
  • matches(pattern) valida em relação a uma expressão regular
  • custom() cria uma lógica de validação personalizada

Você também pode encadear métodos de sanitização como trim(), escape(), e normalizeEmail() para limpar e padronizar dados de entrada antes da validação.

Estrutura e Nomenclatura do Formulário

Observe como o formulário usa o método POST para enviar dados ao servidor no /contact endpoint. Os campos de entrada possuem name atributos que correspondem às chaves esperadas no corpo da requisição do controlador. Essa consistência de nomenclatura é crucial para que o servidor analise e processe corretamente os dados enviados.

Como as views do formulário de contato estão dois níveis abaixo na estrutura de diretórios (forms/contact/), os caminhos relativos para as partials compartilhadas exigem subir dois níveis de diretório. O cabeçalho se torna ../../partials/header e o rodapé se torna ../../partials/footer. Os caminhos de inclusão devem sempre corresponder à localização real da sua view em relação ao diretório de partials.

Para facilitar o acesso ao seu formulário de contato durante o desenvolvimento e os testes, adicione links de navegação à sua partial de cabeçalho. Abra src/views/partials/header.ejs e localize sua lista de navegação existente. Adicione os seguintes itens de lista dentro da sua estrutura <nav><ul>, ao lado dos seus outros links de navegação: 


        <li><a href="/contact">Contact</a></li>
        <li><a href="/contact/responses">Contact Responses</a></li>

O primeiro link fornece acesso fácil ao formulário de contato para os usuários, enquanto o segundo permite que você visualize rapidamente os envios durante o desenvolvimento. Em uma aplicação em produção, você normalmente protegeria a página de respostas com autenticação para que apenas administradores pudessem ver os envios. Por enquanto, deixá-la acessível torna os testes e o desenvolvimento mais convenientes.

9. Testar a Funcionalidade do Formulário

Inicie o seu servidor e teste minuciosamente a funcionalidade do formulário de contato. Foque em verificar se a validação do lado do servidor e as operações do banco de dados funcionam corretamente.

Primeiro, teste os envios bem-sucedidos:

  1. Visite http://127.0.0.1:3000/contact para ver o formulário.
  2. Envie uma mensagem com os campos de assunto e mensagem devidamente preenchidos.
  3. Verifique no console do servidor se há a mensagem de sucesso.
  4. Visite http://127.0.0.1:3000/contact/responses para verificar se o seu envio aparece no banco de dados.

A seguir, teste a validação do lado do servidor enviando intencionalmente formulários que violem as regras de validação. Acompanhe o console do servidor para ver as mensagens de erro de validação:

  • Tente enviar com o campo de assunto vazio.
  • Tente enviar com um assunto de apenas um caractere.
  • Tente enviar com o campo de mensagem vazio.
  • Tente enviar com uma mensagem menor que 10 caracteres.

Em cada caso, o formulário deve redirecionar de volta para a página de contato sem salvar dados inválidos no banco de dados. Você deve ver erros de validação registrados no log do console do servidor que explicam por que o envio foi rejeitado. Verifique na página de respostas que os envios inválidos não aparecem no seu banco de dados.

Verifique também se o seu CSS é carregado corretamente inspecionando o código-fonte da página ou usando as ferramentas de desenvolvedor do navegador para confirmar que contact.css é carregado nas páginas de contato, mas não em outras páginas, como a página inicial ou a página sobre.

10. Adicionar Validação do Lado do Cliente

Agora adicione atributos de validação do HTML5 para melhorar a experiência do usuário, capturando erros de validação antes que o formulário seja enviado. Atualize o seu arquivo src/views/forms/contact/form.ejs modificando os elementos de entrada para incluir atributos de validação: 


        <input type="text" id="subject" name="subject" 
            placeholder="What is this message about?" 
            minlength="2" required>
    

        <textarea id="message" name="message" rows="6" 
            placeholder="Please provide details about your question or feedback..." 
            minlength="10" required></textarea>

O atributo required impede o envio do formulário se o campo estiver vazio, e minlength aplica os mesmos requisitos de comprimento mínimo que a sua validação do lado do servidor. Teste a validação do lado do cliente tentando enviar o formulário com dados inválidos. O navegador deve impedir o envio e exibir mensagens de erro úteis antes que os dados do formulário sejam enviados ao servidor.

Após adicionar a validação do lado do cliente, verifique se os dados válidos ainda são processados corretamente enviando um formulário devidamente preenchido e confirmando se ele aparece na sua página de respostas. A validação do lado do cliente melhora a experiência do usuário, mas a validação do lado do servidor permanece essencial para a segurança, pois a validação do lado do cliente pode ser ignorada.

A Abordagem de Validação em Duas Camadas

Você pode se perguntar por que implementamos a validação duas vezes, tanto no cliente quanto no servidor. Cada camada serve a um propósito diferente e nenhuma pode substituir a outra.

Validação do lado do cliente fornece feedback imediato aos usuários, capturando erros óbvios antes que eles esperem por uma resposta do servidor. Isso melhora a experiência do usuário e reduz requisições desnecessárias ao servidor. No entanto, a validação do lado do cliente pode ser burlada por usuários maliciosos ou desativada no navegador.

Validação do lado do servidor fornece segurança e integridade dos dados. Como é executada em seu servidor, os usuários não podem burlá-la. Esta é a última linha de defesa da sua aplicação contra dados inválidos ou maliciosos. A validação do lado do servidor não é opcional, mesmo quando a validação do lado do cliente está presente.

Em aplicações profissionais, você sempre implementa ambas as camadas. Pense na validação do lado do cliente como uma conveniência para usuários honestos, e na validação do lado do servidor como uma proteção contra todos os usuários, honestos ou não.

Resumo dos Conceitos Principais

Esta Tarefa introduziu vários conceitos importantes para a construção de aplicações web interativas. Você aprendeu como lidar com requisições POST no Express, que são essenciais para processar envios de formulários e outras entradas do usuário. A biblioteca express-validator forneceu ferramentas de validação de nível profissional que garantem a integridade e a segurança dos dados.

A arquitetura MVC que você implementou separa as responsabilidades de forma eficaz: os modelos lidam com operações do banco de dados, os controladores processam requisições e coordenam entre modelos e visualizações, e as visualizações lidam com a apresentação da interface do usuário. Essa organização torna seu código mais fácil de manter e de estender.

Você também implementou a validação do lado do cliente e do lado do servidor, compreendendo que a validação do lado do cliente melhora a experiência do usuário, enquanto a validação do lado do servidor fornece segurança. A abordagem de arquivo SQL que você usou para a configuração do banco de dados segue as melhores práticas da indústria para gerenciar alterações no esquema do banco de dados e mantém o código do seu banco de dados organizado e de fácil manutenção.

Mais importante ainda, você criou uma funcionalidade completa que aceita a entrada do usuário, a valida, a armazena em um banco de dados e fornece uma interface para visualizar os resultados. Esse padrão forma o fundamento para muitas funcionalidades de aplicações web, desde o registro de usuários até sistemas de gerenciamento de conteúdo.

Experimente e Estenda

Tente adicionar campos adicionais ao seu formulário de contato, como um campo de nome ou endereço de e-mail. Lembre-se de atualizar a estrutura da tabela do banco de dados no seu practice.sql arquivo usando ALTER TABLE instruções, adicionar regras de validação para os novos campos no seu arquivo de rotas, atualizar suas funções de modelo para lidar com as colunas adicionais e modificar suas visualizações para exibir as informações adicionais.

Experimente diferentes regras de validação usando o express-validator. Tente adicionar validação de e-mail com isEmail(), validação de número de telefone com matches() e um padrão de expressão regular, ou regras de validação personalizadas que verificam requisitos de conteúdo específicos usando o custom() método.

Considere adicionar um link de navegação simples para o seu formulário de contato na navegação principal do seu site, e adicione um link do formulário de contato para a página de respostas para que você possa visualizar facilmente os envios durante o desenvolvimento. Você também pode experimentar adicionar um botão de exclusão a cada resposta que permite remover os envios do banco de dados.
