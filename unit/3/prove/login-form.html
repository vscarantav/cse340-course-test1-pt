Construindo um Sistema de Login com Gerenciamento de Sessão

Nesta tarefa, você criará um sistema de autenticação completo que permite que os usuários façam login com suas contas registradas, mantenha o estado de login durante as visitas às páginas e forneça acesso seguro a conteúdos protegidos. Isso completa sua trilogia de gerenciamento de usuários, adicionando autenticação baseada em sessão aos sistemas de registro e contato que você já construiu.

Você implementará o gerenciamento de sessão usando sessões do Express armazenadas em seu banco de dados PostgreSQL, criará middleware para proteger rotas que exigem autenticação e construirá uma navegação condicional que se adapta com base no status de login. Esta tarefa enfatiza as melhores práticas de segurança, mantendo os mesmos padrões de arquitetura MVC que você vem usando ao longo desta série.

Ferramentas de IA poderiam concluir esta tarefa para você em apenas alguns minutos. Não ceda a essa tentação. Se você deixar a IA fazer o trabalho por você, perderá o aprendizado de habilidades críticas e colocará sua carreira futura em risco. As habilidades de segurança e autenticação que você desenvolve aqui são fundamentais para o desenvolvimento web. Os empregadores esperam que você entenda como a autenticação funciona, como proteger os dados do usuário e como implementar um gerenciamento de sessão seguro. Se você confiar na IA para essas habilidades fundamentais, poderá ter dificuldades para passar em entrevistas técnicas ou ter sucesso em empregos de desenvolvimento no mundo real. Reserve um tempo para aprender e praticar esses conceitos por conta própria, pois eles são essenciais para o seu futuro como desenvolvedor.

Entendendo o Gerenciamento de Sessão

O HTTP é um protocolo sem estado, o que significa que cada requisição para o seu servidor é independente e não contém memória de requisições anteriores. No entanto, as aplicações web precisam se lembrar de informações sobre os usuários entre as requisições, como se eles estão logados, suas preferências ou o conteúdo do carrinho de compras.

As sessões resolvem esse problema criando um mecanismo de armazenamento temporário que persiste por várias requisições do mesmo usuário. Quando um usuário faz login com sucesso, seu servidor cria uma sessão contendo suas informações de usuário. O servidor envia um identificador de sessão para o navegador do usuário como um cookie, e o navegador inclui automaticamente esse identificador em cada requisição subsequente.

As sessões do Express podem armazenar dados de sessão em vários lugares: memória (que desaparece quando o servidor é reiniciado), arquivos ou bancos de dados. Esta tarefa usa o PostgreSQL para o armazenamento de sessões porque ele oferece persistência, escalabilidade e integração com sua infraestrutura de banco de dados existente. A biblioteca connect-pg-simple cria e gerencia automaticamente a estrutura da tabela de sessões.

Segurança da Sessão

Os identificadores de sessão são essencialmente senhas temporárias que concedem acesso às contas dos usuários. A biblioteca express-session gera automaticamente IDs de sessão criptograficamente seguros e lida com a transmissão segura de cookies. Nunca tente criar seu próprio sistema de gerenciamento de sessão, pois é necessário conhecimento especializado em criptografia e segurança para implementá-lo com segurança.

As sessões têm tempos de expiração para limitar a janela de vulnerabilidade se um ID de sessão for comprometido. Esta tarefa configura sessões de 24 horas, o que significa que os usuários precisarão fazer login novamente após um dia de inatividade.

Preparação

1. Gerar o Segredo da Sessão

Antes de configurar o gerenciamento de sessão, você precisa de um segredo de sessão seguro. Este segredo é usado para assinar e criptografar dados de sessão, protegendo-os contra adulterações. Os segredos de sessão devem ser criptograficamente aleatórios e mantidos em segredo.

Use o Gerador de Segredos JWT para criar um segredo aleatório de pelo menos 128 bits. Adicione-o ao seu .env arquivo: 


        SESSION_SECRET=your_generated_secret_here

Nunca faça commit do seu .env arquivo para o controle de versão nem compartilhe seu segredo de sessão publicamente. Se o seu segredo for comprometido, todas as sessões existentes se tornam vulneráveis a ataques de sequestro. Trate seu segredo de sessão com o mesmo nível de segurança aplicado a senhas de banco de dados e chaves de API.

2. Instalar Pacotes de Sessão

Instale os pacotes de gerenciamento de sessão necessários: 


        pnpm install express-session connect-pg-simple

Esses pacotes trabalham juntos para fornecer a funcionalidade de sessão: o express-session lida com o gerenciamento principal da sessão, enquanto o connect-pg-simple armazena dados de sessão no seu banco de dados PostgreSQL e cria automaticamente a tabela de sessão necessária.

3. Configurar Middleware de Sessão

Configure o middleware de sessão no seu server.js. Adicione estas instruções de importação no topo com suas outras importações: 


        import session from 'express-session';
        import connectPgSimple from 'connect-pg-simple';
        import { caCert } from './src/models/db.js';

Adicione a configuração de sessão à sua estrutura de middleware do Express. Coloque este código logo após a declaração do app const app = express(); mas antes das suas configurações de middleware existentes: 


        // Initialize PostgreSQL session store
        const pgSession = connectPgSimple(session);

        // Configure session middleware
        app.use(session({
            store: new pgSession({
                conObject: {
                    connectionString: process.env.DB_URL,
                    // Configure SSL for session store connection (required by BYU-I databases)
                    ssl: {
                        ca: caCert,
                        rejectUnauthorized: true,
                        checkServerIdentity: () => { return undefined; }
                    }
                },
                tableName: 'session',
                createTableIfMissing: true
            }),
            secret: process.env.SESSION_SECRET,
            resave: false,
            saveUninitialized: false,
            cookie: {
                secure: NODE_ENV.includes('dev') !== true,
                httpOnly: true,
                maxAge: 24 * 60 * 60 * 1000
            }
        }));
Opções de Configuração de Sessão

A configuração de sessão inclui várias opções de segurança importantes. A httpOnly: true impede que o código JavaScript acesse cookies de sessão, protegendo contra ataques XSS. A secure determina se os cookies exigem HTTPS; ela usa HTTP durante o desenvolvimento, mas alterna para HTTPS em produção.

A maxAge controla quanto tempo as sessões duram antes de expirar; aqui está definida para 24 horas (24 * 60 * 60 * 1000 milissegundos). A resave: false previne atualizações desnecessárias de sessão, e saveUninitialized: false previne a criação de sessões para usuários que não fizeram login.

4. Adicionar Sistema de Limpeza de Sessão

O armazenamento de sessão no banco de dados exige manutenção para remover sessões expiradas. Em aplicações web de produção, isso normalmente é tratado por cron jobs (tarefas agendadas que são executadas no nível do sistema operacional) ou agendadores baseados em nuvem. Essas ferramentas externas são executadas independentemente da sua aplicação e podem executar scripts de manutenção em um cronograma fixo.

Para este curso, configurar cron jobs externos exigiria experiência em gerenciamento de servidor e infraestrutura que não está livremente disponível para projetos de alunos. Em vez disso, você implementará um sistema de limpeza interno que executa dentro da sua aplicação Node.js. Embora essa abordagem não seja ideal para sistemas de produção em grande escala (sua limpeza para quando o servidor está offline), ela oferece uma solução prática para ambientes de aprendizado e implantações em pequena escala, além de ensinar os fundamentos de tarefas de manutenção automatizadas.

Crie um novo arquivo em src/utils/session-cleanup.js com o seguinte conteúdo: 


        import db from '../models/db.js';

        /**
         * Removes expired sessions from the database.
         * In production, this would typically be handled by a cron job.
         */
        const cleanupExpiredSessions = async () => {
            try {
                const result = await db.query(
                    `DELETE FROM session WHERE expire < NOW()`
                );

                if (result.rowCount > 0) {
                    console.log(`Cleaned up ${result.rowCount} expired sessions`);
                }
            } catch (error) {
                // Check if the error is due to the session table not existing (PostgreSQL error code 42P01)
                if (error.code === '42P01') {
                    console.log('Session table does not exist yet:\n→ It will be created when the first session is initialized.');
                    return;
                }
                
                // Log actual errors
                console.error('Error cleaning up sessions:', error);
            }
        };

        /**
         * Starts automatic session cleanup that runs every 24 hours.
         * Runs immediately on startup to handle any sessions that expired while server was offline.
         */
        const startSessionCleanup = () => {
            // Run cleanup immediately on startup (catches sessions that expired while offline)
            cleanupExpiredSessions();
            
            // Schedule cleanup to run every 12 hours
            const twelveHours = 12 * 60 * 60 * 1000;
            setInterval(cleanupExpiredSessions, twelveHours);

            console.log('Session cleanup scheduled to run every 12 hours');
        };

        export { startSessionCleanup };

Agora integre o sistema de limpeza na inicialização do seu servidor. Em server.js, adicione esta importação no topo com suas outras importações: 


        import { startSessionCleanup } from './src/utils/session-cleanup.js';

Adicione esta linha logo após a sua configuração de middleware de sessão: 


        // Start automatic session cleanup
        startSessionCleanup();

Esta função de limpeza exclui sessões que passaram do tempo de expiração, impedindo que sua tabela de sessão cresça indefinidamente. A limpeza é executada imediatamente quando seu servidor inicia (lidando com quaisquer sessões que expiraram enquanto o servidor estava offline) e, em seguida, é executada a cada 12 horas automaticamente. A biblioteca connect-pg-simple define automaticamente os tempos de expiração com base na sua maxAge configuração (24 horas neste caso).

Como a limpeza é executada na inicialização, mesmo se o seu servidor ficar offline por dias ou semanas, as sessões expiradas serão limpas assim que o servidor voltar a ficar online. O temporizador de intervalo garante então a manutenção regular enquanto o servidor estiver em execução.

5. Atualizar Middleware Global

Atualize seu middleware global para incluir o gerenciamento do estado de autenticação. Abra src/middleware/global.js e adicione este código na addLocalVariables função: 


        // Convenience variable for UI state based on session state

Nota de Segurança Importante

A isLoggedIn variável é uma funcionalidade conveniente para exibir links de navegação e elementos da interface do usuário adequados. No entanto, ocultar links de navegação não oferece segurança porque os usuários ainda podem digitar URLs diretamente em seus navegadores. Qualquer rota que realmente exija autenticação deve ser protegida com o requireLogin middleware que você criará mais adiante nesta tarefa. Este middleware realiza a verificação de segurança real e redireciona usuários não autorizados para a página de login.

6. Reiniciar e Verificar

Reinicie seu servidor e verifique o console para ver a mensagem de agendamento de limpeza de sessão. A tabela de sessão do connect-pg-simple é criada sob demanda na primeira utilização (quando uma sessão é armazenada), então não se assuste se a tabela não aparecer imediatamente. O objetivo por enquanto é que a inicialização não produza erros. Mais adiante nesta tarefa, você criará a funcionalidade de login que armazena sessões e preenche a tabela de sessão.

A isLoggedIn variável é uma funcionalidade de conveniência para exibir links de navegação e elementos de interface do usuário adequados. No entanto, ocultar links de navegação não oferece segurança, pois os usuários ainda podem digitar URLs diretamente em seus navegadores.

Qualquer rota que realmente exija autenticação deve ser protegida com o requireLogin middleware. Este middleware realiza a verificação de segurança real e redireciona usuários não autorizados para a página de login. Por enquanto, o painel é a única rota protegida. Você irá refatorar outras rotas para usar este middleware em tarefas futuras.

4. Criar middleware de autenticação

Crie um middleware reutilizável para proteger rotas que exigem autenticação. Crie um novo arquivo em src/middleware/auth.js: 


        /**
         * Middleware to require authentication for protected routes.
         * Redirects to login page if user is not authenticated.
         * Sets res.locals.isLoggedIn = true for authenticated requests.
         */
        const requireLogin = (req, res, next) => {
            // Check if user is logged in via session; we can beef this up later with roles and permissions
            if (req.session && req.session.user) {
                // User is authenticated - set UI state and continue
                res.locals.isLoggedIn = true;
                next();
            } else {
                // User is not authenticated - redirect to login
                res.redirect('/login');
            }
        };

        export { requireLogin };

Esta função de middleware verifica a existência de uma sessão de usuário e permite que a requisição continue (para usuários autenticados) ou redireciona para a página de login (para usuários não autenticados). Ao colocá-la em um arquivo de middleware separado, você pode importá-la e usá-la facilmente em qualquer rota que exija autenticação.

Organização do middleware

O middleware de autenticação deve ficar em seu próprio arquivo porque ele fornece funcionalidades das quais muitas partes diferentes da sua aplicação podem precisar. Rotas, controladores e outros middlewares podem importar e usar funções de autenticação sem criar dependências circulares ou confusão arquitetural. Esta separação de responsabilidades torna seu código mais fácil de manter e testar. Se precisar modificar a lógica de autenticação posteriormente, você só precisará alterá-la em um único lugar.

Não remova nem altere o middleware global existente em src/middleware/global.js. A isLoggedIn variável definida lá ainda é necessária para a renderização condicional da interface do usuário, embora as verificações reais de segurança sejam tratadas pelo novo requireLogin middleware.

         * 
         * NOTE: connect.sid is the default session cookie name since we did not
         * specify a custom name when creating the session in server.js.
         */
        const processLogout = (req, res) => {
            // First, check if there is a session object on the request
            if (!req.session) {
                // If no session exists, there's nothing to destroy,
                // so we just redirect the user back to the home page
                return res.redirect('/');
            }

            // Call destroy() to remove this session from the store (PostgreSQL in our case)
            req.session.destroy((err) => {
                if (err) {
                    // If something goes wrong while removing the session from the database:
                    console.error('Error destroying session:', err);

                    /**
                     * Clear the session cookie from the browser anyway, so the client
                     * does not keep sending an invalid session ID.
                     */
                    res.clearCookie('connect.sid');

                    /** 
                     * Normally we would respond with a 500 error since logout did not fully succeed.
                     * Example: return res.status(500).send('Error logging out');
                     * 
                     * Since this is a practice site, we will redirect to the home page anyway.
                     */
                    return res.redirect('/');
                }

                // If session destruction succeeded, clear the session cookie from the browser
                res.clearCookie('connect.sid');

                // Redirect the user to the home page
                res.redirect('/');
            });
        };

        /**
         * Display protected dashboard (requires login).
         */
        const showDashboard = (req, res) => {
            const user = req.session.user;
            const sessionData = req.session;

            // Security check! Ensure user and sessionData do not contain password field
            if (user && user.password) {
                console.error('Security error: password found in user object');
                delete user.password;
            }
            if (sessionData.user && sessionData.user.password) {
                console.error('Security error: password found in sessionData.user');
                delete sessionData.user.password;
            }
            
            // TODO: Render the dashboard view (dashboard)
            // TODO: Pass title: 'Dashboard', user, and sessionData to template
        };

        // Routes
        router.get('/', showLoginForm);
        router.post('/', loginValidation, processLogin);

        // Export router as default, and specific functions for root-level routes
        export default router;
        export { processLogout, showDashboard };

Conclua todos os itens TODO seguindo estas diretrizes:

  • Para o gerenciamento de sessão, armazene os dados do usuário sem o campo de senha: { id, name, email, created_at }
  • Use mensagens de erro genéricas para os usuários ("E-mail ou senha inválidos"), mas logs específicos no console para depuração
  • A processLogin função inclui try-catch porque as funções do modelo não tratan erros por si mesmas. Seu manipulador de erros global capturará erros não tratados, mas o controlador precisa capturar erros esperados (como usuário não encontrado ou senha inválida) para fornecer o feedback adequado ao usuário.
  • Certifique-se de compreender o que a processLogout função está fazendo, lendo os comentários com atenção
  • Em showDashboard, verifique se a senha não está nos objetos user ou sessionData como uma verificação de segurança

7. Integrar rotas de autenticação

        import loginRoutes from './forms/login.js';
        import { processLogout, showDashboard } from './forms/login.js';
        import { requireLogin } from '../middleware/auth.js';

Adicione estas rotas ao seu roteador após as suas outras definições de rota: 


        // Login routes (form and submission)
        router.use('/login', loginRoutes);

        // Authentication-related routes at root level
        router.get('/logout', processLogout);
        router.get('/dashboard', requireLogin, showDashboard);

O formulário de login e as rotas de envio estão agrupados sob /login. No entanto, logout e dashboard existem no nível raiz porque não estão logicamente "sob" o caminho de login. O dashboard usa o requireLogin middleware para garantir que apenas usuários autenticados possam acessá-lo. Esta estrutura mantém as coisas simples por enquanto; em uma tarefa futura de refatoração, você reorganizará as rotas quando tiver várias páginas relacionadas ao dashboard.

9. Teste Seu Sistema de Autenticação

Teste minuciosamente todo o seu sistema de autenticação:

  1. Acesse http://127.0.0.1:3000/login e verifique se o formulário de login é exibido corretamente.
  2. Teste tentativas de login inválido com e-mails inexistentes e senhas incorretas. Verifique o console do seu servidor para ver as mensagens de erro apropriadas.
  3. Registre um novo usuário, se necessário, e faça login com essas credenciais.
  4. Após o login bem-sucedido, verifique se você é redirecionado para o dashboard e consegue ver suas informações de usuário e dados de sessão. Confirme que não há nenhuma propriedade de senha na saída de depuração da sessão.
  5. Verifique se a navegação muda para mostrar as opções de dashboard e logout quando estiver conectado.
  6. Tente acessar http://127.0.0.1:3000/dashboard em uma janela anônima. Você deve ser redirecionado para a página de login.
  7. Teste a funcionalidade de logout e verifique se a sessão é destruída. Após o logout, tente acessar o dashboard novamente e confirme que é redirecionado para o login.
  8. Feche e reabra seu navegador e, em seguida, retorne ao seu site para verificar a persistência da sessão entre sessões do navegador.

Use o pgAdmin para examinar a tabela de sessões e verificar se os dados de sessão estão sendo armazenados adequadamente. A tabela de sessões deve conter entradas com IDs de sessão, dados de sessão criptografados e carimbos de data/hora de expiração. Você também deve ver mensagens no console sobre a limpeza de sessão executada na inicialização e periodicamente.

Os testes de segurança são cruciais para sistemas de autenticação. Sempre teste cenários válidos e inválidos, verifique se as rotas protegidas estão realmente protegidas e confirme se as sessões são criadas e destruídas adequadamente. Preste atenção às mensagens do console para garantir que a lógica de validação e autenticação esteja funcionando corretamente. O mais importante é verificar se as senhas nunca aparecem nos dados ou logs de sessão.

Resumo dos Conceitos-Chave

Esta tarefa completou sua compreensão da autenticação web full-stack, implementando o gerenciamento de sessão, a proteção de rotas e as interações do usuário com estado. Você aprendeu como as sessões do Express preenchem a lacuna entre a natureza sem estado do HTTP e a necessidade de um estado de usuário persistente em aplicações web.

Os padrões de middleware que você implementou demonstram a separação de responsabilidades na segurança web. O requireLogin middleware fornece proteção de autenticação reutilizável que pode ser aplicada a qualquer rota, enquanto o middleware global gerencia o estado da interface do usuário para uma experiência do usuário consistente.

Sua navegação condicional ilustra a diferença entre a conveniência da interface do usuário e as medidas de segurança reais. Enquanto a isLoggedIn variável ajuda a criar experiências de usuário apropriadas, o requireLogin middleware fornece a segurança real, verificando a autenticação no lado do servidor.

A integração do armazenamento de sessão com o PostgreSQL fornece um gerenciamento de sessão persistente e escalável, que sobrevive a reinicializações do servidor e pode lidar com múltiplos usuários concorrentes. O sistema automatizado de limpeza que você implementou imita práticas de manutenção em produção, ensinando sobre tarefas agendadas e manutenção de banco de dados, mesmo que você tenha usado uma solução interna em vez de trabalhos cron externos.

Experimente e Estenda

Tente adicionar rotas protegidas adicionais usando o requireLogin middleware. Aplique este middleware à página de lista de usuários (/register/list) e à página de respostas de contato (/contact/responses) para ver como a proteção de rotas escala em sua aplicação.

Experimente diferentes configurações de duração de sessão para entender as compensações entre a conveniência do usuário e a segurança. Tente implementar a funcionalidade "lembrar-me" estendendo condicionalmente a duração da sessão com base em uma caixa de seleção no formulário de login.
