Introdução aos Bancos de Dados Relacionais

À medida que você continua a construir aplicações web com Express e a arquitetura MVC, logo encontrará uma limitação fundamental: a persistência de dados. Embora suas aplicações possam processar informações e renderizar visualizações dinâmicas, elas carecem de uma maneira confiável de armazenar e recuperar dados além da sessão atual do servidor. É aqui que entram os bancos de dados.

Neste recurso de aprendizagem, você aprenderá sobre bancos de dados relacionais, entenderá por que eles são essenciais para aplicações web e explorará as diferenças entre SQL, MySQL e PostgreSQL. Este fundamento o preparará para integrar a funcionalidade do banco de dados em suas aplicações Express.

O que é um Banco de Dados?

Um banco de dados é uma coleção organizada de informações ou dados estruturados, normalmente armazenados eletronicamente em um sistema de computador. Os bancos de dados são projetados para armazenar, recuperar, atualizar e gerenciar dados de forma eficiente. Eles fornecem uma maneira de persistir informações além da vida de uma única execução de programa.

Pense em um banco de dados como um sistema de arquivo digital onde as informações são armazenadas de maneira organizada, tornando fácil encontrar partes específicas de dados quando necessário. Essa organização permite operações eficientes com dados, mesmo ao lidar com grandes volumes de informações.

Por que precisamos de Bancos de Dados?

No contexto do desenvolvimento web, os bancos de dados resolvem vários problemas críticos:

  • Persistência de Dados: As informações permanecem disponíveis mesmo após reinicializações do servidor ou falhas na aplicação
  • Integridade dos Dados: Regras podem ser aplicadas para garantir que os dados permanecem precisos e consistentes
  • Recuperação Eficiente: Consultas complexas podem ser realizadas para encontrar exatamente os dados de que você precisa
  • Acesso Concorrente: Múltiplos usuários podem acessar e modificar dados simultaneamente
  • Escalabilidade: Bancos de dados bem projetados podem lidar com volumes crescentes de dados e usuários

Sem um banco de dados, suas aplicações Express perderiam todos os seus dados sempre que o servidor fosse reiniciado. Contas de usuário, estado da aplicação e quaisquer informações inseridas pelos usuários desapareceriam, limitando severamente o que suas aplicações podem fazer. Arquivos e imagens não estão armazenados no banco de dados, mas podem ser referenciados e gerenciados por meio de registros do banco de dados. Abordaremos o armazenamento de arquivos em um momento posterior do curso.

Bancos de Dados Relacionais

Bancos de dados relacionais organizam dados em tabelas com linhas e colunas, semelhante a planilhas. Cada tabela representa um tipo específico de entidade (como usuários, produtos ou pedidos), e as linhas representam instâncias dessa entidade. As colunas definem os atributos ou propriedades que cada instância possui.

O que torna os bancos de dados relacionais poderosos é a sua capacidade de estabelecer relacionamentos entre diferentes tabelas. Isso permite modelar cenários complexos do mundo real onde diferentes entidades interagem entre si.

Conceitos-Chave em Bancos de Dados Relacionais

Vamos explorar alguns conceitos fundamentais que formam o fundamento dos bancos de dados relacionais:

Tabelas, Linhas e Colunas

Um banco de dados relacional armazena dados em tabelas (também chamadas de relações). Cada tabela tem um nome e consiste em linhas e colunas:

  • Tabelas: Representam entidades ou conceitos (ex.: usuários, produtos, pedidos)
  • Linhas: Representam registros ou instâncias individuais (ex.: um usuário específico)
  • Colunas: Representam atributos ou propriedades (ex.: user_id, username, email)

Aqui está um exemplo simples de como uma tabela "users" pode parecer: 


        | user_id | username  | email               | join_date  |
        |---------|-----------|---------------------|------------|
        | 1       | johndoe   | john@example.com    | 2023-01-15 |
        | 2       | janedoe   | jane@example.com    | 2023-02-20 |
        | 3       | bobsmith  | bob@example.com     | 2023-03-05 |

Chaves Primárias

Uma chave primária é uma coluna (ou uma combinação de colunas) que identifica de forma única cada linha em uma tabela. No exemplo acima, a coluna "user_id" serve como a chave primária, garantindo que cada registro de usuário possa ser identificado de forma única.

As chaves primárias são essenciais porque elas:

  • Garantem que cada registro seja único dentro de uma tabela
  • Fornecem uma maneira de referenciar registros específicos
  • Permitem relacionamentos entre tabelas diferentes

Chaves Estrangeiras e Relacionamentos

Uma chave estrangeira é uma coluna em uma tabela que se refere à chave primária de outra tabela. Isso cria um relacionamento entre as duas tabelas, permitindo modelar conexões entre diferentes tipos de dados. Por exemplo, se tivermos uma tabela "posts" em uma aplicação de blog, podemos incluir uma coluna "user_id" que referencia o "user_id" na tabela "users": 


        | post_id | title           | content                   | user_id |
        |---------|-----------------|---------------------------|---------|
        | 1       | First Post      | This is my first post!    | 1       |
        | 2       | Hello World     | Hello to everyone!        | 2       |
        | 3       | Database Intro  | Databases are important...| 1       |

Neste exemplo, a coluna "user_id" na tabela "posts" é uma chave estrangeira que referencia a chave primária "user_id" na tabela "users". Esse relacionamento vincula cada postagem ao usuário que a criou, permitindo recuperar facilmente todas as postagens de um usuário específico ou identificar o autor de qualquer postagem. Ao projetar tabelas, é comum definir a chave estrangeira imediatamente após a chave primária na definição da tabela ou ao final da lista de colunas. Isso ajuda a esclarecer a estrutura e os relacionamentos dentro do esquema de banco de dados.

Relacionamentos na Prática

Ao modelar dados para uma aplicação web, você frequentemente precisará expressar conexões entre entidades diferentes. Por exemplo, em uma aplicação de e-commerce, você pode ter clientes que fazem pedidos de produtos. Esses relacionamentos podem ser modelados com chaves estrangeiras conectando tabelas para clientes, pedidos e produtos.

Introdução ao SQL

O SQL (Structured Query Language) é a linguagem padrão para interagir com bancos de dados relacionais. Ele fornece um conjunto de comandos para criar, modificar, consultar e gerenciar dados em um sistema de banco de dados relacional.

O SQL foi desenvolvido na década de 1970 por pesquisadores da IBM e, desde então, tornou-se a linguagem universal para gerenciamento de banco de dados relacional. Ele foi projetado para ser legível por humanos e poderoso o suficiente para lidar com operações de dados complexas.

Operações Básicas de SQL

As operações de SQL podem ser categorizadas em vários tipos:

  • Linguagem de Definição de Dados (DDL): Comandos para criar e modificar estruturas de banco de dados
  • Linguagem de Manipulação de Dados (DML): Comandos para inserir, atualizar e consultar dados
  • Linguagem de Controle de Dados (DCL): Comandos para controlar o acesso aos dados

Aqui estão alguns exemplos de comandos SQL comuns que demonstram esses tipos de operações:

Criando uma Tabela

O seguinte comando SQL cria uma tabela "users" simples: 


        CREATE TABLE users (
            user_id INT PRIMARY KEY,
            username VARCHAR(50) NOT NULL,
            email VARCHAR(100) UNIQUE NOT NULL,
            join_date DATE
        );

Este comando define uma tabela com quatro colunas, especificando o tipo de dado para cada coluna e adicionando restrições como PRIMARY KEY, NOT NULL e UNIQUE para garantir a integridade dos dados. Neste caso, a coluna "user_id" é a chave primária, que identifica de forma única cada usuário, portanto não há necessidade de adicionar uma restrição UNIQUE separada. As colunas "username" e "email" estão marcadas como NOT NULL, o que significa que elas devem ter um valor ao inserir um novo registro. A coluna "email" também está marcada como UNIQUE, garantindo que dois usuários não possam ter o mesmo endereço de e-mail.

Inserindo Dados

Para adicionar dados a uma tabela, você usa o comando INSERT: 


        INSERT INTO users (user_id, username, email, join_date)
        VALUES (1, 'johndoe', 'john@example.com', '2023-01-15');

Consultando Dados

O comando SELECT recupera dados de uma ou mais tabelas: 


        SELECT username, email
        FROM users
        WHERE join_date > '2023-01-01'
        ORDER BY username;

Esta consulta seleciona o nome de usuário (username) e e-mail de todos os usuários que se cadastraram após 1º de janeiro de 2023 e ordena os resultados em ordem alfabética pelo nome de usuário.

Comparando MySQL e PostgreSQL

Embora o SQL seja a linguagem padrão para bancos de dados relacionais, diferentes sistemas de gerenciamento de banco de dados (SGBD) implementam o SQL de maneiras ligeiramente diferentes, com variadas funcionalidades e otimizações. Dois sistemas de banco de dados relacionais populares são o MySQL e o PostgreSQL.

MySQL

O MySQL foi lançado pela primeira vez em 1995 e hoje pertence à Oracle Corporation. É um dos sistemas de banco de dados mais amplamente utilizados, particularmente para aplicações web.

As principais características do MySQL incluem:

  • Facilidade de Uso: Conhecido por ser relativamente fácil de configurar e administrar
  • Desempenho: Otimizado para operações intensivas de leitura, tornando-o adequado para muitas aplicações web
  • Adoção Ampla: Usado por muitas plataformas populares e sistemas de gerenciamento de conteúdo
  • Mecanismos de Armazenamento: Suporta múltiplos mecanismos de armazenamento com diferentes capacidades (InnoDB, MyISAM, etc.)

O MySQL é tradicionalmente popular na pilha LAMP (Linux, Apache, MySQL, PHP/Python/Perl), que tem sido uma configuração comum para desenvolvimento web por muitos anos.

PostgreSQL

O PostgreSQL (frequentemente chamado de "Postgres") foi iniciado em 1986 como o projeto POSTGRES e evoluiu para um sistema de banco de dados open-source avançado.

As principais características do PostgreSQL incluem:

  • Funcionalidades Avançadas: Suporta um amplo array de tipos de dados e funcionalidades avançadas, como herança de tabelas
  • Conformidade com SQL: Adere mais estritamente aos padrões SQL em comparação com muitos outros sistemas de banco de dados
  • Extensibilidade: Pode ser estendido com funções, operadores e tipos de dados personalizados
  • Concorrência e Transações: Excelente suporte para operações concorrentes e transações complexas

O PostgreSQL é frequentemente escolhido para aplicações que exigem consultas complexas, integridade de dados e escalabilidade.

Principais Diferenças

Embora tanto o MySQL quanto o PostgreSQL sejam sistemas de banco de dados poderosos que suportam a linguagem SQL, eles diferem em vários aspectos importantes:

MySQL vs. PostgreSQL: Principais Distinções

Dialeto SQL: Embora ambos usem SQL, existem diferenças sutis de sintaxe. Por exemplo, o PostgreSQL usa aspas duplas para identificadores, enquanto o MySQL tradicionalmente usa crases.

Tipos de Dados: O PostgreSQL suporta uma gama mais ampla de tipos de dados nativos, incluindo tipos numéricos mais precisos, arrays, JSON e tipos personalizados.

Modelo de Concorrência: O PostgreSQL usa MVCC (Multi-Version Concurrency Control) que manipula operações concorrentes de forma diferente da abordagem do MySQL.

Ecossistema: O MySQL tradicionalmente tem sido mais amplamente utilizado no desenvolvimento web, enquanto o PostgreSQL tem sido favorecido para aplicações que exigem operações de dados complexas e rigorosa integridade de dados.

Apesar dessas diferenças, ambos os sistemas são excelentes escolhas para aplicações web. Para este curso, usaremos o PostgreSQL por causa do seu conjunto robusto de funcionalidades, forte adesão aos padrões SQL e capacidades poderosas que servirão bem a você conforme desenvolve aplicações mais complexas.

Bancos de Dados na Arquitetura MVC

Como você vem aprendendo, a arquitetura Model-View-Controller (MVC) separa sua aplicação em três componentes interconectados: Model (responsável pelos dados e lógica de negócios), View (manipula a interface do usuário e a apresentação) e Controller (processa requisições e coordena entre Model e View).

Nesta arquitetura, o banco de dados interage principalmente com a camada Model. O Model representa as estruturas de dados da sua aplicação e contém a lógica para acessar e manipular esses dados. Ao implementar um banco de dados em sua aplicação Express, você criará arquivos de Model que manipulam operações de banco de dados. Esses arquivos conterão funções para criar, ler, atualizar e excluir dados (frequentemente chamadas de operações CRUD).

Organizando Operações do Banco de Dados

Uma abordagem comum é agrupar operações do banco de dados relacionadas em um único objeto. Por exemplo, em um sistema de gerenciamento de usuários, você pode ter um modelo User com métodos como: 


        // User model (simplified example)
        import db from '../database.js'; // Connection to the database
        
        // Create a User object with all user-related database operations
        const User = {
            // Get all users
            getAllUsers: async () => {
                const result = await db.query('SELECT * FROM users');
                return result.rows;
            },
            
            // Get user by ID
            getUserById: async (id) => {
                const result = await db.query('SELECT * FROM users WHERE user_id = $1', [id]);
                return result.rows[0];
            },
            
            // Create new user
            createUser: async (userData) => {
                const result = await db.query(
                    'INSERT INTO users (username, email, join_date) VALUES ($1, $2, $3) RETURNING *',
                    [userData.username, userData.email, new Date()]
                );
                return result.rows[0];
            },
            
            // Update user
            updateUser: async (id, userData) => {
                const result = await db.query(
                    'UPDATE users SET username = $1, email = $2 WHERE user_id = $3 RETURNING *',
                    [userData.username, userData.email, id]
                );
                return result.rows[0];
            },
            
            // Delete user
            deleteUser: async (id) => {
                await db.query('DELETE FROM users WHERE user_id = $1', [id]);
                return { success: true };
            }
        };
        
        export default User;

Esta abordagem cria um namespace claro para todas as operações relacionadas ao usuário. Os controllers importariam e usariam este objeto assim: 


        // In a controller file
        import User from '../models/user.js';
        
        // Route handler for getting a user profile
        const getUserProfile = async (req, res) => {
            const userId = req.params.id;
            const user = await User.getUserById(userId);
            // ...
        };

Abordagens Alternativas

No entanto, nem sempre é necessário agrupar todas as funções do banco de dados em um único objeto, especialmente quando as operações lidam com tipos de dados não relacionados ou funções utilitárias simples. Nesses casos, é comum definir e exportar funções independentes diretamente. Esta abordagem melhora a modularidade e mantém a base de código flexível: 


        // Standalone functions for analytics events
        import db from '../database.js';

        // Log a page visit with arrow function syntax
        const logPageVisit = async (url, userId) => {
            const result = await db.query(
                'INSERT INTO page_visits (url, user_id, visited_at) VALUES ($1, $2, NOW()) RETURNING id',
                [url, userId]
            );
            return result.rows[0].id; // Return the ID of the new visit record
        };

        // Get visit statistics for a specific page
        const getPageVisitStats = async (url) => {
            const result = await db.query(
                `SELECT 
                    COUNT(*) as total_visits,
                    COUNT(DISTINCT user_id) as unique_visitors,
                    MAX(visited_at) as last_visit
                FROM page_visits 
                WHERE url = $1`,
                [url]
            );
            return result.rows[0];
        };

        // Export the functions individually
        export {
            logPageVisit,
            getPageVisitStats
        };

Neste exemplo, o analytics.js exporta funções individuais em vez de um objeto unificado. Esta abordagem funciona bem quando as funções realizam operações simples e focadas, as funções podem ser usadas independentemente em diferentes partes da aplicação, ou não há uma forte necessidade de agrupar as funções sob um objeto comum.

Os controllers importariam e usariam essas funções assim: 


        // In a controller file
        import { logPageVisit, getPageVisitStats } from '../db/analytics.js';
        
        // Middleware to log page visits
        const visitLogger = async (req, res, next) => {
            const userId = req.session.userId || null;
            await logPageVisit(req.originalUrl, userId);
            // ...
        };
        
        // Route handler for admin dashboard
        const getAnalyticsDashboard = async (req, res) => {
            const homepageStats = await getPageVisitStats('/');
            const aboutPageStats = await getPageVisitStats('/about');
            // ...
        };
Escolhendo a Abordagem Correta

Não existe uma regra única para estruturar o código do seu banco de dados. Para entidades primárias em sua aplicação (usuários, produtos, pedidos, etc.), a abordagem de objeto oferece uma organização clara. Para funções utilitárias ou funcionalidades menores, exportações individuais de funções podem ser mais apropriadas. Escolha a abordagem que melhor se adapte às necessidades específicas da sua aplicação.

O Poder dos Bancos de Dados em Aplicações Web

Integrar um banco de dados à sua aplicação Express libera inúmeras possibilidades que seriam difíceis ou impossíveis de alcançar de outra forma. Compreender essas capacidades ajuda a ilustrar por que os bancos de dados são uma parte tão fundamental do desenvolvimento web moderno.

Contas de Usuário e Autenticação

Os bancos de dados permitem armazenar informações do usuário com segurança, tornando possíveis funcionalidades como cadastro de usuários, login e experiências personalizadas. Sem um banco de dados, as credenciais do usuário seriam perdidas quando o servidor reiniciasse, forçando os usuários a se cadastrar novamente toda vez que sua aplicação fosse iniciada.

Gerenciamento de Conteúdo

Para aplicações que gerenciam conteúdo, como postagens de blog, listas de produtos ou conteúdo gerado pelo usuário, os bancos de dados oferecem uma maneira estruturada de armazenar, organizar e recuperar esse conteúdo. Isso habilita funcionalidades como busca, categorização e relacionamentos de conteúdo.

Análise de Dados e Relatórios

Com os dados armazenados em um formato estruturado, você pode executar consultas complexas para analisar tendências, gerar relatórios e obter insights sobre o comportamento dos usuários ou o uso da aplicação. Essa capacidade torna-se cada vez mais valiosa à medida que sua aplicação cresce e acumula dados ao longo do tempo.

Estado e Histórico da Aplicação

Os bancos de dados permitem que sua aplicação mantenha o estado entre sessões e rastreie o histórico, permitindo funcionalidades como histórico de pedidos, logs de atividade e recuperação de dados. Essa persistência cria uma experiência do usuário muito mais rica e habilita funcionalidades críticas para o negócio.

Escalando Além de um Único Servidor

À medida que sua aplicação cresce, pode ser necessário executá-la em vários servidores para lidar com o aumento do tráfego. Um banco de dados fornece um local central para dados que podem ser acessados por várias instâncias de servidor, permitindo o dimensionamento horizontal da arquitetura da sua aplicação.

Resumo dos Conceitos-Chave

Os bancos de dados relacionais são um componente fundamental das aplicações web modernas. Eles fornecem uma maneira estruturada, eficiente e confiável de armazenar e recuperar dados, permitindo funcionalidades que, de outra forma, seriam impossíveis de implementar.

Você aprendeu que os bancos de dados resolvem o problema crítico da persistência de dados em aplicações web, permitindo que as informações sobrevivam a reinicializações do servidor e habilitando funcionalidades como contas de usuário, gerenciamento de conteúdo e análise de dados. Os bancos de dados relacionais organizam os dados em tabelas com relacionamentos estabelecidos, criando um fundamento flexível para modelar cenários do mundo real.

O SQL serve como a linguagem universal para operações de banco de dados, fornecendo comandos padronizados para criar estruturas e manipular dados. Embora tanto o MySQL quanto o PostgreSQL implementem SQL, cada um oferece pontos fortes diferentes, com o PostgreSQL oferecendo funcionalidades mais avançadas e conformidade mais rígida com o SQL.

Por fim, você viu como os bancos de dados se integram à arquitetura MVC por meio da camada Model, onde as operações do banco de dados são organizadas em módulos lógicos que os controllers podem usar para servir conteúdo dinâmico para as views.

O Que Você Aprendeu

Os bancos de dados fornecem persistência — Eles permitem que sua aplicação armazene e recupere dados mesmo após a reinicialização do servidor.

Os bancos de dados relacionais organizam dados em tabelas — As tabelas têm linhas (registros) e colunas (atributos), com relacionamentos entre tabelas estabelecidos por meio de chaves.

O SQL é a linguagem para operações de banco de dados — Ele fornece comandos para criar estruturas, manipular dados e controlar o acesso.

O MySQL e o PostgreSQL são sistemas de banco de dados populares — Eles implementam o SQL com diferentes conjuntos de funcionalidades e otimizações.

No MVC, os bancos de dados interagem com a camada Model — Os modelos encapsulam a lógica para operações de banco de dados, mantendo seu código organizado e fácil de manter.
