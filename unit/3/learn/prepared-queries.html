Consultas Preparadas e Instruções Parametrizadas

Quando sua aplicação web aceita a entrada do usuário e a utiliza em consultas ao banco de dados, você enfrenta um desafio crítico de segurança: como incorporar com segurança essa entrada sem expor seu banco de dados a ataques? Consultas preparadas, também conhecidas como consultas parametrizadas ou instruções preparadas, resolvem esse problema separando o código SQL dos dados do usuário.

Nesta leitura, você aprenderá o que são consultas preparadas, por que elas são essenciais para a segurança do banco de dados e como implementá-las em suas aplicações Node.js usando PostgreSQL. Compreender esse conceito é crucial para as tarefas de formulário de contato, registro e login que você concluirá a seguir.

O Problema: Ataques de Injeção de SQL

Considere um sistema de login simples no qual você precisa verificar as credenciais de um usuário. Você pode se sentir tentado a construir uma consulta como esta: 


        // DANGER: Never do this!
        const email = req.body.email;
        const password = req.body.password;
        const query = `SELECT * FROM users WHERE email = '${email}' AND password = '${password}'`;
        const result = await db.query(query);

Essa abordagem parece direta, mas cria uma vulnerabilidade de segurança grave chamada injeção de SQL. Um atacante poderia inserir um valor de e-mail malicioso como admin@example.com' OR '1'='1 o que transformaria sua consulta em: 


        SELECT * FROM users WHERE email = 'admin@example.com' OR '1'='1' AND password = 'anything'

Como '1'='1' é sempre verdadeiro, essa consulta retorna todos os usuários, independentemente da senha. O atacante acabou de burlar completamente seu sistema de autenticação. Ataques mais sofisticados podem excluir dados, expor informações confidenciais ou até mesmo assumir o controle do seu servidor de banco de dados.

O problema fundamental é que você está misturando código SQL com dados do usuário. Quando você concatena a entrada do usuário diretamente em strings SQL, o banco de dados não consegue distinguir entre a estrutura SQL pretendida e o código malicioso oculto na entrada do usuário.

A Solução: Consultas Preparadas

Consultas preparadas resolvem o problema de injeção de SQL separando a estrutura SQL dos valores dos dados. Em vez de concatenar a entrada do usuário na sua string SQL, você usa marcadores de posição que dizem ao banco de dados onde os dados devem ser inseridos. O banco de dados então manipula os dados separadamente, tratando-os puramente como dados em vez de código executável.

Veja como você escreveria a consulta anterior com segurança usando uma instrução preparada: 


        // SAFE: Using parameterized query
        const email = req.body.email;
        const password = req.body.password;
        const query = 'SELECT * FROM users WHERE email = $1 AND password = $2';
        const result = await db.query(query, [email, password]);

O $1 e $2 são marcadores de posição que o PostgreSQL reconhece como posições de parâmetros. Quando você passa os valores em um array separado, o PostgreSQL sabe que esses são valores de dados, e não código SQL. Não importa o que o usuário digite, isso será tratado como um valor de string em vez de SQL executável.

Se um atacante tentar o mesmo valor de admin@example.com' OR '1'='1 entrada, o PostgreSQL buscará um usuário cujo e-mail seja literalmente igual a toda essa string, incluindo a aspa simples e o código SQL. O ataque falha porque o SQL malicioso nunca é executado como código.

Como Funcionam as Consultas Preparadas

Quando você usa uma consulta preparada, o banco de dados processa seu SQL em duas fases distintas. Primeiro, ele analisa e compila a estrutura SQL com os marcadores de posição, criando um plano de execução. Segundo, ele vincula seus valores de dados a esses marcadores de posição e executa o plano. Como a estrutura SQL já está compilada antes que os dados cheguem, o banco de dados nunca interpreta os dados como código.

Essa separação oferece um benefício adicional: se você executar a mesma consulta várias vezes com valores diferentes, o banco de dados poderá reutilizar o plano de execução compilado, melhorando o desempenho. O banco de dados não precisa analisar e otimizar o SQL a cada execução.

Sintaxe de Parâmetros do PostgreSQL

Diferentes sistemas de banco de dados usam sintaxes diferentes para consultas parametrizadas. O PostgreSQL usa marcadores de posição numerados ($1, $2, $3, etc.) que correspondem a posições no array de valores. Essa numeração explícita torna clara a relação entre os marcadores de posição e os valores, e permite reutilizar o mesmo parâmetro várias vezes, se necessário.

Aqui estão exemplos de padrões de consulta comuns usando a sintaxe de parâmetros do PostgreSQL:

Consulta SELECT Simples


        const getUserByEmail = async (email) => {
            const query = 'SELECT * FROM users WHERE email = $1';
            const result = await db.query(query, [email]);
            return result.rows[0];
        };

Consulta INSERT


        const createUser = async (name, email, password) => {
            const query = 'INSERT INTO users (name, email, password) VALUES ($1, $2, $3) RETURNING *';
            const result = await db.query(query, [name, email, password]);
            return result.rows[0];
        };

Consulta UPDATE


        const updateUserEmail = async (userId, newEmail) => {
            const query = 'UPDATE users SET email = $1, updated_at = CURRENT_TIMESTAMP WHERE id = $2';
            const result = await db.query(query, [newEmail, userId]);
            return result.rowCount > 0;
        };

Consulta DELETE


        const deleteUser = async (userId) => {
            const query = 'DELETE FROM users WHERE id = $1';
            const result = await db.query(query, [userId]);
            return result.rowCount > 0;
        };

Observe que os números dos parâmetros começam em $1, e não em $0. Isso é diferente da indexação de array em JavaScript. O primeiro valor no seu array corresponde a $1, o segundo a $2, e assim por diante.

Consultas Preparadas na Arquitetura MVC

No padrão Model-View-Controller que você usará ao longo deste curso, as consultas ao banco de dados pertencem à camada de modelo. Seus modelos contêm funções que encapsulam operações do banco de dados, e essas funções devem sempre usar consultas preparadas ao incorporar quaisquer dados externos.

Veja como as consultas preparadas se encaixam no padrão MVC que você usará em suas próximas tarefas: 


        // src/models/user-model.js
        import db from './db.js';

        /**
         * Check if an email already exists in the database
         */
        const emailExists = async (email) => {
            const query = 'SELECT * FROM users WHERE email = $1';
            const result = await db.query(query, [email]);
            return result.rows.length > 0;
        };

        /**
         * Save a new user to the database
         */
        const saveUser = async (name, email, hashedPassword) => {
            const query = 'INSERT INTO users (name, email, password) VALUES ($1, $2, $3) RETURNING *';
            const result = await db.query(query, [name, email, hashedPassword]);
            return result.rows[0];
        };

        /**
         * Get a user by their email address
         */
        const getUserByEmail = async (email) => {
            const query = 'SELECT * FROM users WHERE email = $1';
            const result = await db.query(query, [email]);
            return result.rows[0] || null;
        };

        export { emailExists, saveUser, getUserByEmail };

Seus controladores chamarão essas funções de modelo, passando dados de objetos de requisição. As funções de modelo lidam com todas as interações do banco de dados usando consultas preparadas, mantendo sua aplicação segura e mantendo a separação adequada de responsabilidades. 


        // src/controllers/registration-controller.js
        import { emailExists, saveUser } from '../models/user-model.js';

        const processRegistration = async (req, res) => {
            const { name, email, password } = req.body;
            
            // Check if email already exists
            const exists = await emailExists(email);
            if (exists) {
                return res.redirect('/register');
            }
            
            // Hash password and save user
            const hashedPassword = await bcrypt.hash(password, 10);
            const newUser = await saveUser(name, email, hashedPassword);
            
            // Redirect to success page
            res.redirect('/users');
        };

Trabalhando com Dados Complexos

Aplicações reais geralmente precisam trabalhar com múltiplos parâmetros ou estruturas de dados complexas. As consultas preparadas lidam com esses cenários elegantemente, aceitando qualquer número de parâmetros no array de valores.

Múltiplos Parâmetros

Quando você tiver muitos campos para inserir ou atualizar, basta adicionar mais placeholders e valores correspondentes: 


        const createDetailedUser = async (name, email, password, phone, address, city, state, zip) => {
            const query = `
                INSERT INTO users (name, email, password, phone, address, city, state, zip)
                VALUES ($1, $2, $3, $4, $5, $6, $7, $8)
                RETURNING *
            `;
            const result = await db.query(query, [name, email, password, phone, address, city, state, zip]);
            return result.rows[0];
        };

Desestruturando Objetos

Frequentemente, seus dados chegam como um objeto a partir de um envio de formulário ou requisição de API. Você pode desestruturar o objeto para extrair valores para sua consulta preparada: 


        const createUserFromObject = async (userData) => {
            const { name, email, password, phone, address, city, state, zip } = userData;
            const query = `
                INSERT INTO users (name, email, password, phone, address, city, state, zip)
                VALUES ($1, $2, $3, $4, $5, $6, $7, $8)
                RETURNING *
            `;
            const result = await db.query(query, [name, email, password, phone, address, city, state, zip]);
            return result.rows[0];
        };

Consultas com Múltiplas Condições WHERE

A funcionalidade de busca geralmente requer múltiplos filtros opcionais. Você pode construir consultas preparadas que lidam com cláusulas WHERE complexas: 


        const searchUsers = async (searchEmail, searchCity, minDate) => {
            const query = `
                SELECT * FROM users 
                WHERE email LIKE $1 
                AND city = $2 
                AND created_at >= $3
                ORDER BY created_at DESC
            `;
            const result = await db.query(query, [`%${searchEmail}%`, searchCity, minDate]);
            return result.rows;
        };
Mantendo a Ordem dos Parâmetros

A ordem dos valores no seu array deve corresponder exatamente à ordem dos placeholders na sua consulta SQL. Se $1 representa o e-mail na sua consulta, o primeiro elemento no seu array de valores deve ser o e-mail. A ordem incorreta é uma fonte comum de bugs, portanto, certifique-se sempre de que seus placeholders e valores se alinhem corretamente.

O Que Não Pode Ser Parametrizado

Embora as consultas preparadas protejam contra injeção de SQL para valores de dados, você não pode usar parâmetros para palavras-chave SQL, nomes de tabelas ou nomes de colunas. Essas partes da estrutura SQL devem ser definidas diretamente na sua string de consulta: 


        // This WILL work - parameterizing data values
        const query = 'SELECT * FROM users WHERE email = $1';
        await db.query(query, [email]);

        // This will NOT work - cannot parameterize table names
        const query = 'SELECT * FROM $1 WHERE email = $2';
        await db.query(query, [tableName, email]); // ERROR

        // This will NOT work - cannot parameterize column names
        const query = 'SELECT * FROM users WHERE $1 = $2';
        await db.query(query, [columnName, value]); // ERROR

Se você precisar de nomes dinâmicos de tabela ou coluna, você deve validá-los em comparação a uma lista permitida (whitelist) de valores e construir sua string de consulta de acordo. Nunca aceite nomes de tabela ou coluna diretamente da entrada do usuário sem uma validação rigorosa, pois isso cria vulnerabilidades de injeção de SQL que as consultas preparadas não podem prevenir.

As consultas preparadas são sua primeira linha de defesa contra injeção de SQL, mas não substituem outras medidas de segurança, como validação de entrada, aplicar acesso ao banco de dados com privilégios mínimos e auditorias regulares de segurança.

Benefícios Além da Segurança

Embora a prevenção contra injeção de SQL seja o principal motivo para usar consultas preparadas, elas fornecem vários benefícios adicionais que melhoram sua aplicação:

  • Desempenho: O banco de dados pode armazenar em cache e reutilizar planos de execução para consultas preparadas, reduzindo a sobrecarga de análise para consultas executadas com frequência.
  • Clareza do Código: Separar a estrutura SQL dos valores de dados torna suas consultas mais fáceis de ler e entender. A lógica SQL fica imediatamente visível sem ser obscurecida pela concatenação de strings.
  • Segurança de Tipos: O banco de dados lida com a conversão de tipo automaticamente, garantindo que inteiros sejam tratados como inteiros, datas como datas e strings como strings sem conversão manual.
  • Tratamento de Caracteres Especiais: Você nunca precisa se preocupar em escapar aspas, barras invertidas ou outros caracteres especiais. O banco de dados lida com todo o escape automaticamente.
  • Manutenibilidade: Quando você precisa modificar uma consulta, você altera a estrutura SQL em um só lugar, sem se preocupar em quebrar a lógica de concatenação de strings espalhada pelo seu código.

Boas Práticas

Siga estas diretrizes ao trabalhar com consultas preparadas em suas aplicações:

  • Sempre use consultas preparadas para entrada do usuário: Quaisquer dados provenientes dos usuários, seja por meio de formulários, parâmetros de URL ou requisições de API, devem ser passados por parâmetros de consulta preparada.
  • Mantenha as consultas em funções de modelo: Encapsule todas as operações do banco de dados em funções da camada de modelo que utilizam consultas preparadas. Os controladores nunca devem construir consultas SQL diretamente.
  • Verifique a ordem dos parâmetros: Antes de testar uma consulta, rastreie seus marcadores de posição e o array de valores para confirmar que eles se alinham corretamente. Isso evita bugs sutis onde os dados terminam nos campos errados.
  • Use nomes de variáveis descritivos: Nomes de variáveis claros ajudam você a corresponder parâmetros a marcadores de posição. Em vez de val1 e val2, use userEmail e hashedPassword.
  • Manipule valores nulos adequadamente: Se um parâmetro puder ser nulo ou indefinido, considere como sua consulta deve lidar com esse caso. O PostgreSQL suporta verificações IS NULL, mas você precisa estruturar sua consulta adequadamente.
  • Teste com entradas maliciosas: Durante o desenvolvimento, tente deliberadamente ataques de injeção de SQL contra suas consultas para verificar se elas estão devidamente protegidas.
Nunca Misture Abordagens

Não combine concatenação de string com consultas preparadas. Use as consultas preparadas adequadamente com todos os parâmetros passados no array de valores ou não as use de forma alguma. Misturar abordagens cria confusão e frequentemente reintroduz as vulnerabilidades que você está tentando evitar.

Olhando para o Futuro

Em suas próximas tarefas, você aplicará esses conceitos de consultas preparadas ostensivamente. A tarefa do formulário de contato fará você escrever consultas para salvar e recuperar os envios do formulário. A tarefa de registro usará consultas preparadas para verificar e-mails existentes e salvar novas contas de usuário com senhas em hash. A tarefa de login fará consultas ao banco de dados para verificar as credenciais do usuário e gerenciar sessões.

Toda interação com o banco de dados nestas tarefas deve usar consultas preparadas. Isso não é apenas um exercício acadêmico, mas um requisito fundamental de segurança para qualquer aplicação web em produção. Os padrões que você aprende aqui o servirão ao longo de sua carreira como desenvolvedor web.
