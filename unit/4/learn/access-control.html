Controles de Acesso e Contas

Aplicações web modernas atendem a diversos usuários com diferentes necessidades e permissões. Um portal escolar pode precisar distinguir entre alunos visualizando suas notas e instrutores inserindo-as. Uma loja online deve separar clientes que navegam pelos produtos de administradores que gerenciam o inventário. Um sistema de gerenciamento de conteúdo requer diferentes capacidades para autores, editores e administradores. Esta leitura explora como as aplicações implementam essas distinções por meio de sistemas de controle de acesso.

Ao final desta leitura, você compreenderá a diferença fundamental entre autenticação e autorização, explorará diversos métodos para implementar o controle de acesso e aprenderá como sistemas baseados em funções se integram com bancos de dados relacionais. Esse conhecimento fornece o fundamento para construir aplicações que atendem a diferentes tipos de usuários enquanto mantêm a segurança e os limites apropriados de acesso.

Autenticação vs Autorização

Antes de se aprofundar nos sistemas de controle de acesso, devemos distinguir entre dois conceitos frequentemente confundidos: autenticação e autorização. Embora muitas vezes mencionados juntos, eles servem a propósitos fundamentalmente diferentes na segurança da aplicação.

Autenticação: Provando quem você é

A autenticação responde à pergunta "Quem é você?". Quando você faz login em um site com seu nome de usuário e senha, você se autentica provando sua identidade. O sistema verifica se você é quem afirma ser, checando suas credenciais com as informações armazenadas. A autenticação estabelece sua identidade, mas não diz nada sobre o que você pode fazer uma vez dentro do sistema.

Pense na autenticação como mostrar seu ID na entrada de um prédio. O guarda de segurança verifica sua identidade, confirma se você é quem seu ID diz que você é e permite sua entrada. No entanto, seu ID sozinho não determina quais andares você pode acessar ou em quais salas pode entrar depois que estiver lá dentro.

Autorização: Determinando o que você pode fazer

A autorização responde à pergunta "O que você tem permissão para fazer?". Depois de se autenticar (provar sua identidade), o sistema deve determinar suas permissões. Você pode visualizar esta página? Pode editar este conteúdo? Pode excluir estes registros? A autorização controla o acesso a recursos e funcionalidades com base em quem você é.

Continuando com a analogia do prédio, a autorização é como o cartão de acesso que você recebe após mostrar seu ID. Seu cartão pode conceder acesso a determinados andares, mas não a outros, a certas salas, mas não à sala do servidor, em certos horários, mas não fora do expediente. Sua identidade foi verificada (autenticação) e, agora, suas permissões determinam onde você pode ir e o que pode fazer (autorização).

Separação Moderna: OAuth e Autenticação de Terceiros

Aplicações web modernas frequentemente separam completamente a autenticação de sua lógica principal de aplicação. Você provavelmente já viu botões como "Entrar com o Google" ou "Continuar com o GitHub" em sites. Eles usam protocolos como OAuth para delegar a autenticação a terceiros de confiança enquanto mantêm a autorização dentro da própria aplicação.

Quando você clica em "Entrar com o Google", o Google lida com a autenticação (verificando se você é quem afirma ser), mas a aplicação na qual você está entrando ainda controla a autorização (determinando o que você pode fazer). O Google confirma sua identidade e fornece informações básicas sobre você, mas não diz à aplicação se você deve ser um usuário comum ou um administrador. A aplicação faz essa determinação com base em suas próprias regras de autorização.

Essa separação demonstra um princípio importante: autenticação e autorização são preocupações distintas que podem ser tratadas por sistemas diferentes. Neste curso, nós mesmos construiremos tanto a autenticação quanto a autorização, mas entender essa separação ajuda a esclarecer o papel que cada uma desempenha na segurança da aplicação.

Lembre-se da Distinção

A autenticação verifica a identidade ("Você é mesmo o Bob?"), enquanto a autorização determina as permissões ("O que o Bob pode fazer?"). Você pode ter uma sem a outra, e elas frequentemente envolvem sistemas e técnicas diferentes.

Métodos de Controle de Acesso

Assim que os usuários se autenticam, as aplicações precisam de maneiras sistemáticas para controlar o que os usuários autenticados podem acessar e modificar. Aplicações diferentes exigem níveis diferentes de complexidade em seus sistemas de controle de acesso. Um blog simples pode precisar apenas de sinalizadores de permissão básicos, enquanto um sistema empresarial pode exigir hierarquias de papéis sofisticadas e permissões detalhadas. Vamos examinar várias abordagens comuns, progredindo do simples para o mais complexo.

Sinalizadores de Permissão Simples

A forma mais simples de controle de acesso usa sinalizadores booleanos armazenados diretamente nas contas de usuário. Um registro de usuário pode incluir campos como isAdmin, canPost, ou canModerate. Quando a aplicação precisa verificar as permissões, ela simplesmente olha para esses sinalizadores. 


        // Simple permission flag approach
        const user = {
            id: 1,
            username: 'jsmith',
            email: 'jsmith@example.com',
            isAdmin: false,
            canEditPosts: true,
            canDeleteComments: false
        };

        // Checking permissions
        if (user.isAdmin) {
            // Allow access to admin panel
        }

        if (user.canEditPosts) {
            // Show edit button
        }

Esta abordagem funciona bem para aplicações simples com poucos tipos de permissão. É fácil de entender e implementar, exige uma estrutura de banco de dados mínima e fornece verificações de permissão claras e diretas. No entanto, ela escala mal à medida que as aplicações se tornam mais complexas. Adicionar novos tipos de permissão exige alterações no esquema do banco de dados. Gerenciar usuários com muitas combinações de permissões diferentes se torna incômodo, e você pode acabar com dezenas de campos booleanos poluindo sua tabela de usuários.

Listas de Controle de Acesso

As Listas de Controle de Acesso (ACLs, do inglês Access Control Lists) oferecem mais flexibilidade ao listar explicitamente o que cada usuário pode acessar. Em vez de armazenar sinalizadores de permissão gerais, as ACLs associam recursos específicos a usuários específicos e suas ações permitidas. Esta abordagem é comum em sistemas de arquivos e sistemas de gerenciamento de conteúdo nos quais as permissões variam por recurso. 


        // ACL approach - permissions tied to specific resources
        const permissions = [
            { userId: 1, resourceType: 'post', resourceId: 42, action: 'read' },
            { userId: 1, resourceType: 'post', resourceId: 42, action: 'edit' },
            { userId: 1, resourceType: 'post', resourceId: 57, action: 'read' },
            { userId: 2, resourceType: 'post', resourceId: 42, action: 'read' }
        ];

        // Checking if user can edit a specific post
        function canUserEditPost(userId, postId) {
            return permissions.some(p => 
                p.userId === userId && 
                p.resourceType === 'post' && 
                p.resourceId === postId && 
                p.action === 'edit'
            );
        }

As ACLs fornecem controle detalhado sobre recursos individuais. As permissões de usuário podem variar por item específico, tornando-as ideais quando usuários diferentes precisam de acessos diferentes aos mesmos tipos de recursos. Um sistema de gerenciamento de documentos pode usar ACLs para que os usuários possam compartilhar documentos específicos com colegas específicos, mantendo outros privados.

A compensação é a complexidade. As tabelas de ACL podem crescer muito, e verificar permissões exige mais consultas ao banco de dados. O gerenciamento de permissões se torna mais complexo, pois você deve rastrear permissões para cada combinação de usuário-recurso. Para muitas aplicações, esse nível de granularidade é desnecessário.

Controle de Acesso Baseado em Papéis

O Controle de Acesso Baseado em Papéis (RBAC, do inglês Role-Based Access Control) estabelece um equilíbrio entre simplicidade e flexibilidade. Em vez de conceder permissões diretamente aos usuários ou rastrear permissões por recurso, o RBAC agrupa os usuários em papéis. Cada papel tem um conjunto definido de permissões, e os usuários herdam as permissões de seu papel atribuído.

Considere uma aplicação de portal escolar. Em vez de marcar usuários individuais com sinalizadores como canViewGrades, canEditGrades, canManageCourses, e canCreateAccounts, você cria papéis: student, instructor, e admin. Cada papel vem com um conjunto compreendido de recursos. Os alunos podem ver suas próprias notas, os instrutores podem inserir notas para seus cursos e os administradores podem gerenciar todo o sistema. 


        // RBAC approach - permissions associated with roles
        const user = {
            id: 1,
            username: 'jsmith',
            email: 'jsmith@example.com',
            roleId: 2  // References a role
        };

        const roles = {
            1: { name: 'user', permissions: ['view_profile', 'edit_own_profile'] },
            2: { name: 'admin', permissions: ['view_profile', 'edit_own_profile', 'edit_any_profile', 'manage_users'] }
        };

        // Checking permissions through roles
        function hasPermission(user, permission) {
            const role = roles[user.roleId];
            return role.permissions.includes(permission);
        }

O RBAC oferece várias vantagens que o tornam popular em muitas aplicações. Os papéis se alinham naturalmente com a estrutura organizacional (funcionário, gerente, administrador). O gerenciamento de permissões se torna mais simples porque você gerencia as permissões dos papéis em vez das permissões individuais dos usuários. Quando você precisa alterar o que os gerentes podem fazer, você atualiza o papel de gerente uma única vez em vez de atualizar centenas de registros de usuários individuais. Novos usuários podem receber acesso adequado rapidamente ao atribuir-lhes um papel.

O RBAC lida com o caso comum de forma elegante: a maioria dos usuários se encaixa em categorias pré-definidas com permissões padrão. O sistema permanece flexível o suficiente para adicionar novos papéis à medida que as necessidades evoluem, mantendo-se simples o suficiente para ser compreendido e mantido. Esta é a abordagem que vamos implementar neste curso.

Escolhendo a Abordagem Correta

Sinalizadores de permissão simples funcionam bem para aplicações com poucos tipos de permissão e variação mínima entre os usuários. As ACLs se destacam quando as permissões devem variar significativamente por recurso individual. O RBAC oferece o melhor equilíbrio para aplicações onde os usuários se encaixam naturalmente em categorias com necessidades de permissão semelhantes. A maioria das aplicações web se beneficia da combinação de simplicidade e flexibilidade do RBAC.

Controle de Acesso Baseado em Papéis e Bancos de Dados Relacionais

Entender como o RBAC se integra a bancos de dados relacionais é crucial para a implementação. A estrutura do banco de dados afeta diretamente a eficiência com que você pode verificar permissões e a facilidade com que pode modificar as definições de papéis. Vamos examinar o design típico do banco de dados e depois explorar como o código da aplicação usa essa estrutura para impor o controle de acesso.

Estrutura de Banco de Dados para RBAC

Um sistema RBAC básico tipicamente envolve pelo menos duas tabelas: uma tabela users e uma tabela roles. A tabela de usuários contém informações da conta (nome de usuário, e-mail, hash de senha) além de uma referência de chave estrangeira para a tabela de papéis. A tabela de papéis define os papéis disponíveis e pode opcionalmente armazenar configurações específicas de cada papel. 


        -- Roles table defines available roles
        CREATE TABLE roles (
            role_id SERIAL PRIMARY KEY,
            role_name VARCHAR(50) UNIQUE NOT NULL,
            role_description TEXT
        );

        -- Users table references roles
        CREATE TABLE users (
            user_id SERIAL PRIMARY KEY,
            username VARCHAR(50) UNIQUE NOT NULL,
            email VARCHAR(100) UNIQUE NOT NULL,
            password_hash VARCHAR(255) NOT NULL,
            role_id INTEGER REFERENCES roles(role_id),
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );

        -- Seed with basic roles
        INSERT INTO roles (role_name, role_description) VALUES 
            ('user', 'Standard user with basic access'),
            ('admin', 'Administrator with full system access');

Esta estrutura estabelece um relacionamento: cada usuário tem exatamente uma função, e cada função pode ser atribuída a muitos usuários (um relacionamento de um para muitos). Quando você consulta um usuário, pode facilmente fazer um join com a tabela de funções para recuperar as informações da função dele. Quando você precisa atualizar as definições de função, você modifica a tabela de funções, e todos os usuários com essa função refletem imediatamente a alteração.

Sistemas mais sofisticados podem incluir tabelas adicionais. Uma permissions tabela poderia enumerar todas as ações possíveis no sistema. Uma role_permissions tabela de junção associaria então as funções às suas permissões específicas, permitindo a atribuição dinâmica de permissões sem alterações de código. Para este curso, manteremos a estrutura mais simples, com a lógica de permissão manipulada no código da aplicação e não no banco de dados.

Aplicando o Controle de Acesso no Código da Aplicação

A estrutura do banco de dados armazena funções, mas o código da aplicação as aplica. Em aplicações Express, funções de middleware fornecem uma maneira elegante de verificar permissões antes de permitir o acesso a rotas. Essas funções de middleware examinam a função do usuário autenticado e permitem que a requisição prossiga ou negam o acesso. 


        // Middleware to require specific role
        function requireRole(roleName) {
            return (req, res, next) => {
                // Assumes user object is attached to req by authentication middleware
                if (!req.user) {
                    return res.status(401).send('Not authenticated');
                }

                if (req.user.role_name !== roleName) {
                    return res.status(403).send('Insufficient permissions');
                }

                // User has required role, allow request to proceed
                next();
            };
        }

        // Using the middleware on routes
        app.get('/admin/dashboard', requireRole('admin'), (req, res) => {
            res.render('admin/dashboard');
        });

        app.post('/admin/users/:id/edit', requireRole('admin'), (req, res) => {
            // Only admins can reach this code
            // Handle user editing logic
        });

Esse padrão é comum e eficaz. As funções de middleware são executadas antes dos manipuladores de rota, fornecendo um ponto de verificação onde o acesso pode ser verificado. Se o usuário não tiver permissão, o middleware envia uma resposta de erro e interrompe a requisição. Se o usuário tiver permissão, o middleware chama next(), permitindo que a requisição continue para o manipulador de rota.

Os controladores também podem verificar permissões para um controle de acesso mais detalhado. Enquanto o middleware funciona bem para proteção no nível da rota (rotas inteiras exigem funções específicas), os controladores lidam com lógicas específicas da situação (usuários podem editar seu próprio perfil, mas administradores podem editar qualquer perfil). 


        // Controller with role-specific logic
        async function editUserProfile(req, res) {
            const targetUserId = req.params.userId;
            const currentUser = req.user;

            // Admins can edit anyone, users can only edit themselves
            const canEdit = currentUser.role_name === 'admin' || 
                           currentUser.user_id === parseInt(targetUserId);

            if (!canEdit) {
                return res.status(403).send('You cannot edit this profile');
            }

            // Proceed with editing logic
            // ...
        }

Essa combinação de middleware para requisitos amplos de função e lógica de controlador para cenários de permissão específicos fornece um controle de acesso flexível e fácil de manter. O middleware mantém usuários não autorizados afastados de seções inteiras da aplicação, enquanto a lógica do controlador lida com as nuances de quem pode fazer o que em quais recursos específicos.

Nunca Confie no Controle de Acesso do Lado do Cliente

Ocultar botões ou itens de menu com base nas funções do usuário melhora a experiência do usuário, mas não fornece segurança. Os usuários podem manipular seu navegador ou fazer requisições HTTP diretas para burlar restrições do lado do cliente. Sempre aplique o controle de acesso no servidor usando middleware e lógica de controlador. Os controles do lado do cliente são para conveniência, os controles do lado do servidor são para segurança.

Considerações de Segurança

A implementação do controle de acesso envolve mais do que apenas verificar funções. Vários princípios de segurança ajudam a garantir que seu sistema de autorização permaneça robusto e seguro.

Princípio do Menor Privilégio: Os usuários devem ter as permissões mínimas necessárias para realizar suas tarefas. Em caso de dúvida, restrinja o acesso em vez de concedê-lo. Você sempre pode adicionar permissões mais tarde se os usuários precisarem delas, mas remover permissões depois que os usuários as esperam é mais difícil e pode introduzir vulnerabilidades de segurança se for ignorado.

Defesa em Profundidade: Múltiplas camadas de segurança fornecem melhor proteção do que qualquer mecanismo único. Verifique as permissões no nível da rota com middleware, verifique-as novamente nos controladores antes de operações sensíveis e valide a entrada do usuário em todo o processo. Se uma verificação falhar ou for burlada, outras verificações ainda poderão impedir o acesso não autorizado.

Falhe de Forma Segura: Quando as verificações de permissão encontrarem erros ou condições inesperadas, elas devem negar o acesso em vez de permiti-lo. Se você não puder determinar se um usuário deve ter acesso (talvez porque o banco de dados esteja temporariamente indisponível), o padrão seguro é negar a requisição. Falhar de forma segura evita que erros temporários se tornem vulnerabilidades de segurança.

Audite Ações Importantes: Registre em log eventos significativos, especialmente aqueles que envolvem alterações de privilégios ou acesso a dados sensíveis. Se um administrador editar a conta de outro usuário, registre em log quem fez a alteração, quando ela aconteceu e o que mudou. Os logs de auditoria ajudam a detectar acesso não autorizado e fornecem responsabilidade.

Erros Comuns de Segurança

Evite armadilhas comuns: Não exponha informações de função no JavaScript do lado do cliente que os usuários possam manipular. Não confie apenas na ocultação de elementos da interface do usuário para restringir o acesso. Não use identificadores de função previsíveis que os usuários possam adivinhar. Não pule verificações de autorização em endpoints de API ou manipuladores AJAX. Cada rota que modifica dados ou exibe informações sensíveis precisa de verificações de autorização adequadas.

Conclusão

Os sistemas de controle de acesso formam uma parte crucial da segurança de aplicações, determinando o que os usuários autenticados podem ver e fazer. Compreender a distinção entre autenticação (provar a identidade) e autorização (determinar permissões) fornece o fundamento para construir sistemas seguros. Diferentes métodos de controle de acesso atendem a diferentes necessidades: sinalizadores de permissão simples para cenários básicos, Listas de Controle de Acesso para permissões detalhadas de recursos, e Controle de Acesso Baseado em Funções para o caso comum em que os usuários se enquadram naturally em categorias.

O RBAC se integra elegantemente com bancos de dados relacionais por meio de relacionamentos de chave estrangeira entre usuários e papéis. O middleware do Express oferece uma maneira limpa e de fácil manutenção para impor requisitos de papéis, verificando permissões antes que as rotas sejam executadas. Os controladores lidam com a lógica específica de cada situação, na qual os requisitos de permissão variam com base no contexto, como usuários editando suas próprias informações em comparação com administradores editando as informações de qualquer pessoa.

Na próxima Tarefa, você implementará um sistema de dois papéis com usuários padrão e administradores. Esta prática mão na massa consolidará sua compreensão de como o RBAC funciona em aplicações reais. Você criará estruturas de banco de dados para dar suporte aos papéis, escreverá middlewares para impor os requisitos de papéis e construirá controladores que respeitem os limites de permissão. Essas habilidades se transferem diretamente para sistemas mais complexos e aplicações maiores, onde o controle de acesso se torna ainda mais crítico.
