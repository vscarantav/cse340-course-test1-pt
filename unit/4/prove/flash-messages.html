Implementando Mensagens Flash

Nesta tarefa, você implementará um sistema de mensagens flash que permite que sua aplicação exiba mensagens de feedback temporárias aos usuários após envios de formulário e redirecionamentos. Mensagens flash resolvem um problema fundamental no desenvolvimento web: como fornecer feedback ao usuário após um redirecionamento. Quando um usuário envia um formulário e seu servidor o redireciona para outra página, você precisa de uma maneira de comunicar informações de sucesso ou erro através desse redirecionamento.

Você criará um middleware personalizado que gerencia o armazenamento e a recuperação de mensagens flash usando sessões, integrará esse middleware à sua aplicação e atualizará seus controladores de formulário existentes (contato, registro e login) para usar mensagens flash em vez de logs de console. Ao final desta tarefa, seus usuários verão mensagens de feedback claras e úteis exibidas diretamente no navegador em vez de ocultas em logs do servidor.

Entendendo o Padrão de Mensagens Flash

Antes de implementar mensagens flash, você precisa entender o problema que elas resolvem. Considere o que acontece quando um usuário envia um formulário em seu site. O navegador envia uma requisição POST para o seu servidor com os dados do formulário. Seu servidor valida os dados e os processa. Se a validação falhar, você deseja informar ao usuário o que deu errado. Se a validação for bem-sucedida, você deseja confirmar que a ação foi concluída.

O desafio surge do padrão Post-Redirect-Get, uma boa prática de desenvolvimento web que evita envios duplicados de formulários. Após processar uma requisição POST, seu servidor envia uma resposta de redirecionamento (status 302 ou 303) que diz ao navegador para fazer uma nova requisição GET para uma URL diferente. Esse redirecionamento impede que os usuários reenviem acidentalmente o formulário se atualizarem a página.

No entanto, redirecionamentos criam um problema para o feedback do usuário. A requisição POST e a requisição GET subsequente são requisições HTTP completamente separadas com objetos de requisição e resposta separados. Você não pode simplesmente anexar dados à resposta porque o redirecionamento a descarta. Você precisa de uma maneira de armazenar a mensagem durante a requisição POST e recuperá-la durante a requisição GET.

Mensagens flash resolvem esse problema armazenando mensagens temporárias na sessão. A sessão persiste entre as requisições porque é identificada por um cookie que o navegador envia a cada requisição para o seu servidor. Durante a requisição POST, você armazena a mensagem na sessão. Durante a requisição GET do redirecionamento, você recupera a mensagem da sessão e a exibe ao usuário. Após exibir a mensagem uma vez, você a exclui da sessão para que ela não apareça novamente nos carregamentos subsequentes de página.

Por que as Sessões são Necessárias

As mensagens flash dependem do armazenamento de sessão porque as sessões são o único mecanismo nativo no Express que persiste dados entre requisições HTTP separadas para o mesmo usuário. Sua aplicação já possui o middleware de sessão configurado a partir da tarefa de login, portanto as mensagens flash se integram perfeitamente ao seu sistema de autenticação existente.

Instruções da Tarefa

1. Criar o Middleware de Flash

Crie um novo arquivo em src/middleware/flash.js. Este middleware fornecerá a funcionalidade principal para armazenar e recuperar mensagens flash. Adicione o seguinte código: 


        /**
         * Flash Message Middleware
         * 
         * Provides temporary message storage that survives redirects but is consumed on render.
         * Messages are stored in the session and organized by type (success, error, warning, info).
         * 
         * Usage in controllers:
         *   req.flash('success', 'Message text')  // Store a message
         *   req.flash('error')                    // Get all error messages
         *   req.flash()                           // Get all messages (all types)
         */

        /**
         * Initialize flash message storage and provide access methods
         */
        const flashMiddleware = (req, res, next) => {
            // Track if flash messages were set (need to save session before redirect)
            let sessionNeedsSave = false;
            
            // Override res.redirect to save session before redirecting
            const originalRedirect = res.redirect.bind(res);
            res.redirect = (...args) => {
                if (sessionNeedsSave && req.session) {
                    // Save session before redirecting
                    req.session.save(() => {
                        originalRedirect.apply(res, args);
                    });
                } else {
                    originalRedirect.apply(res, args);
                }
            };
            
            /**
            * The flash function handles both setting and getting messages
            * - Called with 2 args (type, message): stores a new message
            * - Called with 1 arg (type): retrieves and clears messages of that type
            * - Called with 0 args: retrieves and clears all messages
            */
            req.flash = function(type, message) {
                // Guard: If session doesn't exist (e.g., after session.destroy()), 
                // return early to prevent errors. Flash messages require a session to store.
                if (!req.session) {
                    // If setting a message (both type and message provided), can't do without session
                    if (type && message) {
                        return; // Silently fail - no session to store in
                    }
                    // If getting messages, return empty structure
                    return { success: [], error: [], warning: [], info: [] };
                }
                
                // Initialize flash storage if it doesn't exist
                if (!req.session.flash) {
                    req.session.flash = {
                        success: [],
                        error: [],
                        warning: [],
                        info: []
                    };
                }

                // SETTING: Two arguments means we're storing a new message
                if (type && message) {
                    // Ensure this message type's array exists
                    if (!req.session.flash[type]) {
                        req.session.flash[type] = [];
                    }
                    // Add the message to the appropriate type array
                    req.session.flash[type].push(message);
                    // Mark that session needs to be saved before redirect
                    sessionNeedsSave = true;
                    return;
                }

                // GETTING ONE TYPE: One argument means retrieve messages of that type
                if (type && !message) {
                    const messages = req.session.flash[type] || [];
                    // Clear this type's messages after retrieving
                    req.session.flash[type] = [];
                    return messages;
                }

                // GETTING ALL: No arguments means retrieve all message types
                const allMessages = req.session.flash || {
                    success: [],
                    error: [],
                    warning: [],
                    info: []
                };

                // Clear all flash messages after retrieving
                req.session.flash = {
                    success: [],
                    error: [],
                    warning: [],
                    info: []
                };

                return allMessages;
            };

            next();
        };

        /**
        * Make flash function available to all templates via res.locals
        * This middleware must run AFTER flashMiddleware
        */
        const flashLocals = (req, res, next) => {
            // Attach the flash function to res.locals so templates can access it
            // The function is NOT called here, just made available
            // Messages are only consumed when a template calls flash()
            res.locals.flash = req.flash;
            next();
        };

        /**
        * Combined flash middleware that runs both functions in the correct order
        * Import and use this as a single middleware function in your application
        */
        const flash = (req, res, next) => {
            flashMiddleware(req, res, () => {
                flashLocals(req, res, next);
            });
        };

        export default flash;

Leia o código e os comentários com atenção. O middleware exporta uma única flash função que executa internamente duas funções de middleware em sequência. A flashMiddleware função anexa o flash() método ao objeto de requisição, enquanto flashLocals disponibiliza essa função para os modelos por meio de res.locals.

A req.flash() função se comporta de maneira diferente com base no número de argumentos que você passa. Com dois argumentos (tipo e mensagem), ela armazena uma nova mensagem na sessão. Com um argumento (tipo), ela recupera todas as mensagens desse tipo e as limpa. Sem argumentos, ela recupera todas as mensagens de todos os tipos e as limpa. Esse design oferece flexibilidade para diferentes casos de uso, mantendo a API simples.

Entendendo a Organização de Mensagens

As mensagens flash são organizadas por tipo no armazenamento da sessão. Cada tipo (success, error, warning, info) tem seu próprio array que pode conter várias mensagens. Essa organização permite que você exiba diferentes tipos de mensagens com diferentes estilos, facilitando para os usuários distinguirem entre ações bem-sucedidas, erros, avisos e informações gerais.

2. Integre o Middleware Flash na Sua Aplicação

Abra o seu server.js arquivo e importe o middleware flash perto do topo do arquivo com suas outras importações de middleware. Adicione esta linha após as importações de sessão: 


        import flash from './src/middleware/flash.js';

Em seguida, registre o middleware flash na sua aplicação. Este middleware deve ser executado após o middleware de sessão (porque ele usa sessões), mas antes das suas rotas (para que as rotas possam usar req.flash()). Localize onde você registra sua função de middleware global e adicione o middleware flash imediatamente após ela: 


        // Global middleware (sets res.locals variables)
        app.use(addLocalVariables);

        // Flash message middleware (must come after session and global middleware)
        app.use(flash);

A ordem importa aqui. O middleware de sessão deve ser executado primeiro para criar req.session. O middleware flash é executado em seguida para adicionar req.flash() e res.locals.flash. Suas rotas são executadas por último para que possam usar mensagens flash.

3. Adicione a Exibição de Mensagens Flash à Sua Parcial de Cabeçalho

Abra src/views/partials/header.ejs e adicione o código de exibição da mensagem flash imediatamente após a tag de fechamento </header>. Esse posicionamento garante que as mensagens flash apareçam no topo do conteúdo da página, logo abaixo da navegação, tornando-as imediatamente visíveis para os usuários. 


        </header>

        <% 
            const messages = flash();
            const hasMessages = Object.values(messages).some(arr => arr.length > 0);
        %>

        <% if (hasMessages) { %>
            <div class="flash-messages">
                <% Object.keys(messages).forEach(type => { %>
                    <% messages[type].forEach(message => { %>
                        <div class="flash <%= type %>">
                            <%= message %>
                        </div>
                    <% }); %>
                <% }); %>
            </div>
        <% } %>

Este código de modelo chama flash() para recuperar todas as mensagens, o que as limpa automaticamente da sessão. Em seguida, ele verifica se existem mensagens em todos os tipos. Se mensagens forem encontradas, ele percorre cada tipo em um laço e exibe cada mensagem em uma div com classes CSS apropriadas para estilização.

A abordagem Object.keys(messages) itera dinamicamente por todos os tipos de mensagens, o que significa que este código funcionará mesmo se você adicionar novos tipos de mensagens no futuro. Cada div de mensagem recebe duas classes CSS: uma classe geral flash para estilização comum e uma classe de tipo específica (success, error, warning ou info) para estilização específica do tipo.

Abra public/css/main.css e adicione estilos para mensagens flash. Esses estilos devem tornar as mensagens visualmente distintas, fáceis de ler e comunicar claramente seu propósito por meio de cores e design.

A borda esquerda fornece um destaque visual que torna o tipo de mensagem imediatamente reconhecível. As cores de fundo são sutis, mas perceptíveis, e as cores do texto garantem uma boa legibilidade em relação aos seus fundos.

5. Atualize o Controlador do Formulário de Contato

Abra src/controllers/forms/contact.js e substitua todas as instruções console.log() e console.error() por mensagens flash. Localize a função handleContactSubmission. Seu código atual provavelmente possui um tratamento de erro de validação que usa console.error() e um bloco try-catch que usa console.log(). Você precisa substituir estes por mensagens flash.

Antes de começar, altere o redirecionamento de sucesso para usar res.redirect('/contact') em vez de res.redirect('/contact/responses'). Isso garante que todos os usuários (incluindo usuários não autenticados) possam ver a mensagem flash confirmando seu envio. A mensagem flash agora serve como confirmação, portanto, redirecionar para a página de respostas não é mais necessário.

Para erros de validação, substitua seus registros de log no console por este código: 


        // Inside your validation error check
        if (!errors.isEmpty()) {
            // Store each validation error as a separate flash message
            errors.array().forEach(error => {
                req.flash('error', error.msg);
            });
            return res.redirect('/contact');
        }

Para envios bem-sucedidos, substitua seus registros de log no console por este código logo antes do redirecionamento: 


        // After successfully saving to the database
        req.flash('success', 'Thank you for contacting us! We will respond soon.');
        res.redirect('/contact');

Para erros no bloco catch, mantenha o console.error() para registros de log no servidor, mas adicione uma mensagem flash para o usuário: 


        catch (error) {
            console.error('Error saving contact form:', error);
            req.flash('error', 'Unable to submit your message. Please try again later.');
            res.redirect('/contact');
        }

Observe o padrão: os erros de validação percorrem todas as mensagens de erro em um laço e criam mensagens flash separadas, envios bem-sucedidos criam uma mensagem flash de sucesso e erros inesperados criam uma mensagem flash de erro. O console.error() permanece no bloco catch porque registra detalhes técnicos no servidor para depuração, enquanto a mensagem flash fornece feedback amigável ao usuário no navegador.

Verifique Seu Trabalho

Se você quiser verificar sua implementação, aqui está a função handleContactSubmission completa com mensagens flash devidamente integradas: 


            const handleContactSubmission = async (req, res) => {
                const errors = validationResult(req);
                
                if (!errors.isEmpty()) {
                    // Store each validation error as a separate flash message
                    errors.array().forEach(error => {
                        req.flash('error', error.msg);
                    });
                    return res.redirect('/contact');
                }
    
                try {
                    const { subject, message } = req.body;
                    await createContactForm(subject, message);
                    req.flash('success', 'Thank you for contacting us! We will respond soon.');
                    res.redirect('/contact');
                } catch (error) {
                    console.error('Error saving contact form:', error);
                    req.flash('error', 'Unable to submit your message. Please try again later.');
                    res.redirect('/contact');
                }
            };

Sempre chame req.flash() antes de res.redirect(). A mensagem flash deve ser armazenada na sessão antes que o redirecionamento ocorra. Se você redirecionar primeiro, a mensagem não estará disponível quando a próxima página for carregada.

6. Atualize o Controlador do Formulário de Registro

Abra src/controllers/forms/registration.js e aplique o mesmo padrão de mensagem flash que você acabou de aprender. Assim como no formulário de contato, certifique-se de alterar o redirecionamento de sucesso para usar res.redirect('/login') em vez de res.redirect('/register/list'). Isso garante que todos os usuários (incluindo usuários não autenticados) possam ver a mensagem flash confirmando seu registro. A mensagem flash agora serve como confirmação, portanto, redirecionar para a página da lista não é mais necessário.

Em seguida, localize a processRegistration função e atualize-a seguindo estes requisitos:

  • Erros de validação: Use o mesmo padrão do formulário de contato (percorra os erros em um laço e crie mensagens flash)
  • Verificação de e-mail duplicado: Quando emailExists() retornar verdadeiro, use req.flash('warning', ...) com uma mensagem apropriada informando ao usuário que uma conta já existe
  • Registro bem-sucedido: Use req.flash('success', ...) com uma mensagem confirmando o registro e redirecione para /login
  • Erros do bloco catch: Mantenha console.error() para registro de log do servidor e adicione req.flash('error', ...) para feedback do usuário

Este controller demonstra três tipos de mensagens diferentes: error para falhas de validação, warning para o cenário de e-mail duplicado (que não é exatamente um erro, mas algo de que o usuário deve estar ciente) e success para registro concluído.

7. Atualizar o Controller do Formulário de Login

Abra src/controllers/forms/login.js e aplique o padrão de mensagem flash à processLogin função. Siga estes requisitos:

  • Erros de validação: Use o mesmo padrão que você aprendeu (faça um laço e crie mensagens flash)
  • Usuário não encontrado: Use req.flash('error', 'Invalid email or password')
  • Senha inválida: Use req.flash('error', 'Invalid email or password')
  • Login bem-sucedido: Use req.flash('success', ...) com uma mensagem de boas-vindas personalizada usando o nome do usuário
  • Erros do bloco catch: Mantenha console.error() e adicione req.flash('error', ...)
Consideração de Segurança

Observe que ambos os cenários "usuário não encontrado" e "senha inválida" usam exatamente a mesma mensagem: "E-mail ou senha inválidos." Isso impede que atacantes determinem quais endereços de e-mail têm contas no seu sistema, uma vulnerabilidade de segurança chamada enumeração de contas. Nunca revele se o e-mail existe ou se a senha estava incorreta; sempre use uma mensagem genérica para falhas de autenticação.

8. Teste suas Mensagens Flash

Reinicie seu servidor e teste exaustivamente as mensagens flash em todos os seus formulários. Os testes exigem a verificação de cenários de sucesso e de erro para garantir que as mensagens sejam exibidas corretamente em todas as situações.

Ignorando a Validação do Lado do Cliente para Testes

Seus formulários possuem atributos de validação do HTML5 como required, minlength, e type="email" que impedem o envio do formulário quando os campos são inválidos. Essa validação do lado do cliente ocorre no navegador antes que a requisição alcance seu servidor, tornando impossível testar sua validação do lado do servidor e mensagens flash com dados incorretos.

Para testar a validação do lado do servidor, você precisa ignorar a validação do lado do cliente. Adicione o atributo novalidate à tag de abertura do seu formulário. Por exemplo, na visualização do seu formulário de contato, altere <form method="POST" action="/contact"> para <form method="POST" action="/contact" novalidate>. Isso diz ao navegador para ignorar a validação do HTML5 e enviar o formulário diretamente para o seu servidor.

Após os testes, remova o atributo novalidate. A validação do lado do cliente fornece feedback imediato aos usuários e reduz requisições desnecessárias ao servidor, portanto você deseja que ela esteja ativa em produção. Use novalidate apenas durante o desenvolvimento para testar sua lógica de validação do lado do servidor.

Testes do Formulário de Contato: Adicione novalidate ao seu formulário de contato. Envie com dados válidos e confirme se uma mensagem de sucesso é exibida. Envie com assunto ou mensagem em branco e confirme se as mensagens de erro de validação são exibidas. Envie com um assunto muito curto (menos de 2 caracteres) e verifique se a mensagem de erro é exibida. Atualize a página após ver uma mensagem e confirme se ela desaparece.

Testes do Formulário de Registro: Adicione novalidate ao seu formulário de registro. Envie com credenciais válidas e exclusivas e confirme se uma mensagem de sucesso aparece na página de login (verifique se o redirecionamento funcionou e se a mensagem sobreviveu). Envie com e-mails ou senhas divergentes e confirme se as mensagens de erro aparecem para cada falha de validação. Tente se registrar com um e-mail que já existe e confirme se a mensagem de aviso aparece. Envie com uma senha muito curta e verifique se o erro de validação é exibido.

Testes do Formulário de Login: Adicionar novalidate ao seu formulário de login. Faça login com credenciais válidas e confirme se a mensagem de boas-vindas personalizada aparece no painel. Tente fazer login com um e-mail que não existe no banco de dados e confirme se a mensagem "E-mail ou senha inválido" aparece. Tente fazer login com um e-mail válido, mas com a senha errada, e confirme se a mesma mensagem de erro genérica aparece. Envie com o campo de senha vazio e confirme se a mensagem de erro de validação é exibida.

Preste atenção ao estilo e ao posicionamento das mensagens. As mensagens devem aparecer no topo da área de conteúdo, abaixo da navegação, estar claramente visíveis e usar cores que comuniquem sua finalidade. Mensagens de sucesso devem parecer positivas (verde), erros devem ser notáveis (vermelho), avisos devem ser de advertência (amarelo) e mensagens informativas devem ser neutras (azul).

Testes do Comportamento das Mensagens Flash

As mensagens flash devem sobreviver a redirecionamentos, mas não a atualizações de página. Após enviar um formulário e ver uma mensagem, atualize a página. A mensagem deve desaparecer porque chamar flash() no modelo limpa automaticamente as mensagens da sessão. Esse comportamento de exibição única é o que as torna mensagens "flash". Navegue para longe da página e retorne. Nenhuma mensagem deve aparecer porque ela já foi consumida durante o primeiro carregamento da página.

Resumo dos Conceitos-Chave

Esta tarefa apresentou as mensagens flash, um padrão baseado em sessão para exibir comentários temporários do usuário entre redirecionamentos. As mensagens flash resolvem o desafio fundamental do padrão Post-Redirect-Get, no qual os redirecionamentos impedem a passagem direta de dados entre requisições.

Você criou um middleware personalizado que gerencia o armazenamento e a recuperação de mensagens flash por meio da sessão. O middleware fornece uma única flash() função que armazena e recupera mensagens, com a recuperação consumindo e excluindo automaticamente as mensagens da sessão. As mensagens são organizadas por tipo (sucesso, erro, aviso, info) em arrays, permitindo que várias mensagens do mesmo tipo sejam exibidas juntas.

Você integrará a exibição de mensagens flash no seu partial do cabeçalho, criando um local consistente para o feedback do usuário em todas as páginas sem duplicação de código. A lógica dinâmica do modelo usa Object.keys() para iterar pelos tipos de mensagem, tornando o sistema extensível para qualquer número de tipos sem alterações de código.

Em seus controladores, você substituiu os logs do console por mensagens flash, melhorando a experiência do usuário ao exibir o feedback diretamente na interface em vez de escondido nos logs do servidor. Você praticou o padrão de armazenar mensagens antes de redirecionar e confirmou que as mensagens sobrevivem aos redirecionamentos, mas são consumidas na renderização, evitando que sejam exibidas repetidamente.

Experimente e Estenda

Agora que você tem um sistema de mensagens flash funcional, considere estas melhorias para aprofundar seu entendimento:

  • Adicione uma mensagem flash à sua rota de logout para confirmar quando os usuários tiverem saído com sucesso
  • Adicione uma mensagem flash ao seu middleware de autenticação (src/middleware/auth.js) para notificar os usuários quando eles tentarem acessar uma rota protegida sem estarem logados
  • Aprimore a exibição de mensagens flash com ícones usando uma biblioteca de ícones como Font Awesome ou Lucide
  • Adicione um botão de fechar às mensagens flash usando JavaScript no lado do cliente para que os usuários possam fechá-las manualmente

Conclusão

As mensagens flash são um padrão fundamental em aplicações web que seguem a abordagem Post-Redirect-Get. Ao armazenar mensagens temporárias em sessões, elas preenchem a lacuna entre o processamento do formulário e o feedback do usuário, garantindo que os usuários entendam os resultados de suas ações. O padrão é simples, confiável e funciona sem exigir JavaScript, tornando-o uma ferramenta essencial para criar aplicações web responsivas e amigáveis para o usuário.

A implementação baseada em middleware que você criou demonstra padrões importantes do Express: middleware personalizado para aumento de requisição, res.locals para dados do modelo e armazenamento em sessão para persistir o estado entre requisições. Esses padrões se aplicam além das mensagens flash a muitas outras funcionalidades que você construirá conforme continua desenvolvendo aplicações web.
