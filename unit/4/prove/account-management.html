Gerenciamento de Contas e Controle de Acesso Baseado em Papéis

Nesta tarefa, você implementará o controle de acesso baseado em papéis em sua aplicação, transformando-a de um sistema onde todos os usuários autenticados têm permissões idênticas para um onde diferentes usuários podem realizar diferentes ações com base em seus papéis atribuídos. Você criará a estrutura do banco de dados para suportar papéis, modificará seu sistema de autenticação para incluir informações sobre papéis, construirá middleware de autorização para proteger rotas e criará funcionalidades de gerenciamento de contas que respeitem os limites de permissão.

Ao final desta tarefa, você terá um sistema funcional onde usuários padrão podem editar suas próprias informações de conta, enquanto administradores podem gerenciar todas as contas de usuário. Você usará o sistema de mensagens flash que implementou anteriormente para fornecer um feedback claro quando as verificações de autorização forem bem-sucedidas ou falharem.

Instruções da Tarefa

1. Criar Estrutura de Banco de Dados para Papéis

Abra o seu src/models/sql/practice.sql arquivo e adicione as seguintes instruções SQL ao final. Essas instruções criam uma tabela de papéis (roles), adicionam uma referência de papel à sua tabela de usuários, povoam os papéis iniciais e atribuem os usuários existentes ao papel padrão. 


        -- Roles table for role-based access control
        CREATE TABLE IF NOT EXISTS roles (
            id SERIAL PRIMARY KEY,
            role_name VARCHAR(50) UNIQUE NOT NULL,
            role_description TEXT,
            created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        );

        -- Add role_id column to users table if it doesn't exist
        DO $$
        BEGIN
            IF NOT EXISTS (
                SELECT 1 FROM information_schema.columns 
                WHERE table_name = 'users' AND column_name = 'role_id'
            ) THEN
                ALTER TABLE users 
                ADD COLUMN role_id INTEGER REFERENCES roles(id);
            END IF;
        END $$;

        -- Seed roles (idempotent - safe to run multiple times)
        INSERT INTO roles (role_name, role_description) 
        VALUES 
            ('user', 'Standard user with basic access'),
            ('admin', 'Administrator with full system access')
        ON CONFLICT (role_name) DO NOTHING;

        -- Set the default value of role_id to the 'user' role so new inserts without role_id are handled automatically
        DO $$
        DECLARE
            user_role_id INTEGER;
        BEGIN
            SELECT id INTO user_role_id FROM roles WHERE role_name = 'user';
            IF user_role_id IS NOT NULL THEN
                EXECUTE format(
                    'ALTER TABLE users ALTER COLUMN role_id SET DEFAULT %s',
                    user_role_id
                );
            END IF;
        END $$;

        -- Update existing users without a role to default 'user' role
        DO $$
        DECLARE
            user_role_id INTEGER;
        BEGIN
            SELECT id INTO user_role_id FROM roles WHERE role_name = 'user';
            IF user_role_id IS NOT NULL THEN
                UPDATE users 
                SET role_id = user_role_id 
                WHERE role_id IS NULL;
            END IF;
        END $$;

Reinicie o seu servidor e verifique as alterações no pgAdmin. Você deve ver uma tabela roles com dois papéis, e sua tabela de usuários deve ter uma role_id coluna com todos os usuários existentes atribuídos ao papel "user".

Entendendo Chaves Estrangeiras

A restrição de chave estrangeira (REFERENCES roles(id)) cria um relacionamento entre as tabelas users e roles. O PostgreSQL garante que qualquer role_id valor na tabela users deve corresponder a um id que exista na tabela roles. Você não pode atribuir um usuário a um papel que não existe, e não pode excluir um papel ao qual usuários estejam atribuídos atualmente.

Você precisa de contas de teste para verificar se o controle de acesso baseado em papéis funciona corretamente. A abordagem mais simples é registrar contas através da sua aplicação e, em seguida, promover uma delas para admin usando o pgAdmin.

Use o seu formulário de registro para criar três contas de teste com esta senha: Test1234!

  • admin@example.com
  • user1@example.com
  • user2@example.com

Após registrar essas contas, abra o pgAdmin e execute este SQL para promover a primeira conta a admin: 


        -- Promote admin@example.com to admin role
        UPDATE users 
        SET role_id = (SELECT id FROM roles WHERE role_name = 'admin')
        WHERE email = 'admin@example.com';

Agora você tem uma conta de admin e duas contas de usuário padrão, todas com a mesma senha para facilitar os testes.

3. Incluir Informações de Papel em Sessões

Quando os usuários fazem login, sua aplicação precisa recuperar as informações do papel deles e armazená-las na sessão. Abra src/models/forms/login.js e atualize a findUserByEmail função para fazer a junção (join) com a tabela roles: 


        const findUserByEmail = async (email) => {
            const query = `
                SELECT 
                    users.id, 
                    users.name, 
                    users.email, 
                    users.password, 
                    users.created_at,
                    roles.role_name AS "roleName"
                FROM users
                INNER JOIN roles ON users.role_id = roles.id
                WHERE LOWER(users.email) = LOWER($1)
                LIMIT 1
            `;
            const result = await db.query(query, [email]);
            return result.rows[0] || null;
        };

O controlador de login já remove a senha antes de armazenar o usuário na sessão, então roleName será incluído automaticamente em req.session.user. Reinicie o seu servidor, faça login e verifique se o papel está na sessão adicionando o seguinte à sua exibição do painel entre as linhas de e-mail e data de criação: 


        <div class="user-detail">

Você deve ver "user" ou "admin" dependendo da conta com a qual fez login. Em uma aplicação de produção, você normalmente não exibiria informações de papel na interface do usuário, mas isso é útil para testes.

4. Criar Middleware de Autorização

Abra src/middleware/auth.js. Atualmente, este arquivo possui requireLogin middleware que verifica a autenticação. Adicione uma nova função fábrica de middleware que verifica a autorização (permissões baseadas em papéis).

Adicione esta função após requireLogin: 


        /**
         * Middleware factory to require specific role for route access
         * Returns middleware that checks if user has the required role
         * 
         * @param {string} roleName - The role name required (e.g., 'admin', 'user')
         * @returns {Function} Express middleware function
         */
        const requireRole = (roleName) => {
            return (req, res, next) => {
                // Check if user is logged in first
                if (!req.session || !req.session.user) {
                    req.flash('error', 'You must be logged in to access this page.');
                    return res.redirect('/login');
                }

                // Check if user's role matches the required role
                if (req.session.user.roleName !== roleName) {
                    req.flash('error', 'You do not have permission to access this page.');
                    return res.redirect('/');
                }

                // User has required role, continue
                next();
            };
        };

Atualize a instrução de exportação: 


        export { requireLogin, requireRole };

Esta fábrica de middleware retorna uma função que verifica se o usuário autenticado possui a função necessária. O comentário em seu atual requireLogin mencionou "podemos aprimorar isso mais tarde com funções e permissões" - esta é essa melhoria.

5. Adicionar modelos de gerenciamento de conta

Abrir src/models/forms/registration.js e adicione três novas funções para o gerenciamento de contas. Adicione estas funções antes da instrução de exportação: 


        /**
         * Retrieve a single user by ID with role information
         */
        const getUserById = async (id) => {
            const query = `
                SELECT 
                    users.id,
                    users.name,
                    users.email,
                    users.created_at,
                    roles.role_name AS "roleName"
                FROM users
                INNER JOIN roles ON users.role_id = roles.id
                WHERE users.id = $1
            `;
            const result = await db.query(query, [id]);
            return result.rows[0] || null;
        };

        /**
         * Update a user's name and email
         */
        const updateUser = async (id, name, email) => {
            const query = `
                UPDATE users 
                SET name = $1, email = $2, updated_at = CURRENT_TIMESTAMP
                WHERE id = $3
                RETURNING id, name, email, updated_at
            `;
            const result = await db.query(query, [name, email, id]);
            return result.rows[0] || null;
        };

        /**
         * Delete a user account
         */
        const deleteUser = async (id) => {
            const query = 'DELETE FROM users WHERE id = $1';
            const result = await db.query(query, [id]);
            return result.rowCount > 0;
        };

Atualize a instrução de exportação para incluir estas novas funções:

Adicione estas duas funções de controlador antes das definições de rota: 


        /**
         * Display the edit account form
         * Users can edit their own account, admins can edit any account
         */
        const showEditAccountForm = async (req, res) => {
            const targetUserId = parseInt(req.params.id);
            const currentUser = req.session.user;

            const targetUser = await getUserById(targetUserId);
            
            if (!targetUser) {
                req.flash('error', 'User not found.');
                return res.redirect('/register/list');
            }

            // Check permissions: users can edit themselves, admins can edit anyone
            const canEdit = currentUser.id === targetUserId || currentUser.roleName === 'admin';
            
            if (!canEdit) {
                req.flash('error', 'You do not have permission to edit this account.');
                return res.redirect('/register/list');
            }

            res.render('forms/registration/edit', {
                title: 'Edit Account',
                user: targetUser
            });
        };

        /**
         * Process account edit form submission
         */
        const processEditAccount = async (req, res) => {
            const errors = validationResult(req);

            if (!errors.isEmpty()) {
                errors.array().forEach(error => {
                    req.flash('error', error.msg);
                });
                return res.redirect(`/register/${req.params.id}/edit`);
            }

            const targetUserId = parseInt(req.params.id);
            const currentUser = req.session.user;
            const { name, email } = req.body;

            try {
                const targetUser = await getUserById(targetUserId);
                
                if (!targetUser) {
                    req.flash('error', 'User not found.');
                    return res.redirect('/register/list');
                }

                // Check permissions
                const canEdit = currentUser.id === targetUserId || currentUser.roleName === 'admin';
                
                if (!canEdit) {
                    req.flash('error', 'You do not have permission to edit this account.');
                    return res.redirect('/register/list');
                }

                // Check if new email already exists (and belongs to different user)
                const emailTaken = await emailExists(email);
                if (emailTaken && targetUser.email !== email) {
                    req.flash('error', 'An account with this email already exists.');
                    return res.redirect(`/register/${targetUserId}/edit`);
                }

                // Update the user
                await updateUser(targetUserId, name, email);

                // If user edited their own account, update session
                if (currentUser.id === targetUserId) {
                    req.session.user.name = name;
                    req.session.user.email = email;
                }

                req.flash('success', 'Account updated successfully.');
                res.redirect('/register/list');
            } catch (error) {
                console.error('Error updating account:', error);
                req.flash('error', 'An error occurred while updating the account.');
                res.redirect(`/register/${targetUserId}/edit`);
            }
        };

Adicione estas rotas antes da instrução de exportação:

7. Criar controlador de exclusão de conta

No mesmo src/controllers/forms/registration.js arquivo, adicione a função de controlador de exclusão: 


        /**
         * Process account deletion
         * Only admins can delete accounts, and they cannot delete themselves
         */
        const processDeleteAccount = async (req, res) => {
            const targetUserId = parseInt(req.params.id);
            const currentUser = req.session.user;

            // Only admins can delete accounts
            if (currentUser.roleName !== 'admin') {
                req.flash('error', 'You do not have permission to delete accounts.');
                return res.redirect('/register/list');
            }

            // Prevent admins from deleting their own account
            if (currentUser.id === targetUserId) {
                req.flash('error', 'You cannot delete your own account.');
                return res.redirect('/register/list');
            }

            try {
                const deleted = await deleteUser(targetUserId);
                
                if (deleted) {
                    req.flash('success', 'User account deleted successfully.');
                } else {
                    req.flash('error', 'User not found or already deleted.');
                }
            } catch (error) {
                console.error('Error deleting user:', error);
                req.flash('error', 'An error occurred while deleting the account.');
            }

            res.redirect('/register/list');
        };

Adicione a rota de exclusão: 


        /**
         * POST /register/:id/delete - Delete user account
         */
        router.post('/:id/delete', requireLogin, processDeleteAccount);

11. Testar sua implementação

Teste minuciosamente seu sistema de controle de acesso baseado em funções com diferentes tipos de usuários:

Como um usuário padrão (user1@example.com / Test1234!):

  • Acesse /register/list e verifique se você vê um botão Editar apenas no seu próprio cartão de usuário
  • Clique em Editar no seu cartão e altere seu nome ou e-mail
  • Tente acessar /register/2/edit (a página de edição de outro usuário) e verifique se você é redirecionado com uma mensagem de erro

Como administrador (admin@example.com / Test1234!):

  • Acesse /register/list e verifique se você vê botões Editar em todos os cartões e botões Excluir em todos os cartões, exceto no seu próprio
  • Edite a conta de outro usuário e verifique se as alterações são salvas
  • Exclua uma das contas de usuário de teste e verifique se ela desaparece da lista
  • Verifique se você não pode excluir sua própria conta (nenhum botão Excluir aparece no seu cartão)

Como um visitante não autenticado:

  • Acesse /register/list e verifique se você vê a lista, mas nenhum botão Editar ou Excluir
  • Tente acessar /register/1/edit diretamente e verifique se você é redirecionado para o login

Resumo dos conceitos-chave

Esta Tarefa demonstrou o controle de acesso baseado em funções em uma aplicação funcional. Você criou estruturas de banco de dados para armazenar funções e associá-las aos usuários usando relacionamentos de chave estrangeira. Sua lógica de configuração é idempotente, o que significa que pode ser executada com segurança várias vezes sem criar dados duplicados.

Você modificou seu sistema de autenticação para recuperar e armazenar informações de função em sessões, tornando as decisões de autorização eficientes. O padrão de fábrica de middleware de autorização (requireRole) fornece verificação de função reutilizável para rotas. A autorização no nível do controlador lida com verificações de permissão específicas de recursos, como permitir que os usuários editem apenas suas próprias contas.

Suas exibições agora mostram diferentes capacidades com base no contexto do usuário. Isso melhora a experiência do usuário ao ocultar ações que os usuários não podem realizar, enquanto a autorização no lado do servidor garante a segurança real. A combinação de proteção por middleware, lógica de controlador e interface do usuário condicional cria um sistema de controle de acesso robusto.

Princípios de Segurança Aplicados

A Autorização no Lado do Servidor É Obrigatória: Toda rota que modifica dados deve verificar permissões no servidor. Sua lógica de middleware e controlador impõe quem pode editar e excluir contas. Ocultar botões na interface do usuário evita confusão, mas não fornece segurança.

Defesa em Profundidade: Sua aplicação verifica permissões em vários lugares. O middleware bloqueia rotas para usuários não autorizados. Os controladores verificam as permissões antes das operações. As exibições ocultam botões para ações indisponíveis. Se uma camada falhar, outras camadas ainda fornecerão proteção.

Prevenção de Danos Próprios: Seu controlador de exclusão impede que administradores excluam suas próprias contas. Sem essa verificação, um administrador poderia acidentalmente ficar sem acesso ao sistema.

Restrições de Chave Estrangeira: O relacionamento de chave estrangeira entre usuários e funções impede dados órfãos. Você não pode atribuir um usuário a uma função que não existe e não pode excluir uma função que os usuários possuem atualmente. Essa proteção em nível de banco de dados evita inconsistências de dados.
