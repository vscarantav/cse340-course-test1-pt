Revisão de Código da Unidade 2

Nesta Tarefa, você aprenderá a realizar revisões de código eficazes examinando os sites de prática Express.js de seus colegas de equipe diretamente no GitHub. A revisão de código é uma habilidade fundamental no desenvolvimento profissional que ajuda as equipes a manter a qualidade, identificar problemas precocemente e compartilhar conhecimento.

Você aprenderá o que procurar no código Express.js, praticará o uso das ferramentas de revisão do GitHub e fornecerá feedbacks construtivos para ajudar seus colegas de equipe a melhorar seus projetos. Como seus colegas de equipe podem estar em diferentes estágios da refatoração para MVC, você aprenderá a avaliar o código em vários níveis de organização.

Entendendo o que Procurar

Antes de revisar o código, você precisa saber o que constitui um código Express.js bom versus um problemático. Aqui estão as principais áreas e problemas comuns, organizados se o código foi refatorado para a arquitetura MVC ou não.

Problemas de Remoção de Funcionalidades (Todos os Projetos Devem Tratar)

Independentemente do progresso da refatoração, todos os projetos devem ter removido a funcionalidade de produtos como parte da Tarefa de MVC. Verifique:

❌ Funcionalidade de Produtos Não Removida Adequadamente

  • Manipuladores de rota ainda existem: Procure em server.js ou arquivos de controlador para quaisquer rotas como /products
  • Links de navegação permanecem: Verifique views/partials/header.ejs para links de páginas de produtos
  • Arquivos de exibição não excluídos: Procure por products.ejs ou arquivos semelhantes no diretório views
  • Código comentado: Código de produtos que foi comentado em vez de excluído

✅ Funcionalidade de Produtos Removida Adequadamente

  • Nenhuma rota relacionada a produtos em qualquer lugar da base de código
  • Menus de navegação atualizados para remover links de produtos
  • Todos os arquivos de modelo relacionados a produtos excluídos
  • Nenhum código de produto comentado restante

Problemas de Código Pré-Refatoração

Se seu colega de equipe ainda não começou a refatoração MVC, fique atento a estes problemas tradicionais do Express.js:

❌ Estrutura Ruim (Monolítica)


        [project-root]
        ├── server.js        # Everything in one file
        ├── style.css        # Should be in public/css/
        ├── home.ejs         # Should be in views/
        └── logo.png         # Should be in public/images/

❌ Problemas Comuns no server.js


        // Unnecessary 'next' parameter
        app.get('/catalog', (req, res, next) => {
            res.render('catalog'); // next is never used
        });

        // Poor variable names
        const x = req.params.cat;
        const y = req.query.sort || 'def';
        
        // Missing validation
        app.get('/catalog/:id', (req, res) => {
            const courseId = req.params.id; // What if this is invalid?
            res.render('course-detail', { id: courseId });
        });

Problemas de Código Pós-Refatoração (Arquitetura MVC)

Se seu colega de equipe iniciou ou concluiu a refatoração MVC, procure por estes problemas de organização e arquitetura:

❌ Organização MVC Ruim


        [project-root]
        ├── src/
        │   ├── controllers/
        │   │   └── everything.js    # All controllers in one file
        │   ├── models/
        │   │   └── data.js          # Generic naming
        │   └── middleware/
        │       └── stuff.js         # Unclear purpose
        └── server.js

✅ Boa Estrutura MVC


        [project-root]
        ├── src/
        │   ├── controllers/
        │   │   ├── catalog/
        │   │   │   └── catalog.js
        │   │   ├── index.js
        │   │   └── routes.js
        │   ├── models/
        │   │   └── catalog/
        │   │       └── catalog.js
        │   ├── middleware/
        │   │   └── global.js
        │   └── views/
        └── server.js

❌ Controladores com Preocupações Mistas


        // Controller doing too much
        export const catalogPage = (req, res) => {
            // Data should be in models, not controllers
            const courses = {
                'CS121': { title: 'Intro Programming' },
                'CS162': { title: 'Intro CS' }
            };
            
            // Business logic should be in models too
            const sortedCourses = Object.values(courses).sort((a, b) => 
                a.title.localeCompare(b.title)
            );
            
            res.render('catalog', { courses: sortedCourses });
        };

✅ Implementação Limpa de Controlador


        import { getAllCourses } from '../../models/catalog/catalog.js';

        export const catalogPage = (req, res) => {
            const courses = getAllCourses(); // Data comes from model
            
            res.render('catalog', {
                title: 'Course Catalog',
                courses: courses
            });
        };

❌ Middleware Dividido Desnecessariamente


        // Multiple middleware functions doing similar things
        app.use(addImportantLocalVariables);
        app.use(addOptionalLocalVariables);
        app.use(addMoreStuff);

✅ Middleware Consolidado


        // Single middleware that handles all res.locals setup
        app.use(addLocalVariables);

Prática Rápida

Olhe para este código e identifique os problemas (isso pode ser encontrado em um server.js monolítico ou em um arquivo de controlador): 


        app.get('/catalog/:cat/:id', (req, res, next) => {
            const c = req.params.cat;
            const i = req.params.id;
            
            if(c==='courses'){
            res.render('course-detail',{category:c,id:i});
            }else{
            res.send('Not found');
            }
        });
Clique para ver os problemas
  • Não utilizado next parâmetro → Remova do cabeçalho da função
  • Nomes de variáveis ruins (c, i) → Use nomes completos como category e id
  • Formatação inconsistente → Adicione linhas em branco e recuo de forma consistente
  • Usando res.send() → Use res.render() e realmente renderize uma página de erro ou modelo
  • Nenhuma validação para req.params.id → Adicione validação ou falhe de forma elegante

Diretrizes de Comunicação

Escreva issues e feedbacks como se estivesse ajudando um colega de equipe, não dando nota a ele. Lembre-se de que o código em diferentes estágios de refatoração exige diferentes tipos de feedback:

Seja Útil e Adaptável

  • Explique o porquê: "Isso pode causar erros se os usuários inserirem dados inválidos" ou "A separação do MVC torna o código mais fácil de manter"
  • Sugira soluções: Mostre a correção, não apenas aponte os problemas
  • Seja específico: "Linha 23 no server.js" ou "função catalogPage em src/controllers/catalog/catalog.js"
    • Você pode referenciar uma linha de código específica nesta issue vinculando-a diretamente. Passe o mouse sobre o número da linha, clique nas … (reticências) e selecione "Reference in new issue". O GitHub criará automaticamente uma issue com um link direto para essa linha de código.
  • Seja positivo: Aponte o que funciona bem, juntamente com o que precisa ser melhorado
  • Seja compreensivo: Se alguém estiver no meio de uma refatoração, reconheça seu progresso enquanto sugere melhorias

Mantenha Simples

  • Foque nas issues mais importantes que os ajudarão a aprender
  • Não crie issues para preferências secundárias de formatação
  • Se você não tiver certeza sobre a abordagem de refatoração usada, faça perguntas em vez de fazer suposições
  • Priorize issues funcionais em relação às estilísticas

Exemplos de um Bom Tom de Feedback

  • Encorajador: "Ótimo trabalho ao iniciar a refatoração do MVC! Notei um pequeno problema com a estrutura do controller..."
  • Educativo: "Isso funciona, mas mover os dados para um arquivo de model seguiria melhor os princípios do MVC porque..."
  • Construtivo: "Vejo que você ainda não começou a refatoração do MVC. Aqui estão algumas áreas nas quais se concentrar quando o fizer..."

Instruções da Tarefa

1. Obter links do repositório

Compartilhe o link do seu repositório do GitHub com seus colegas de equipe e obtenha pelo menos dois links de repositório para revisar. Você revisará esses projetos inteiramente por meio da interface web do GitHub.

2. Revisar usando o GitHub

Para cada repositório, navegue pelos arquivos usando a interface web do GitHub. Como os colegas de equipe podem estar em diferentes estágios de refatoração do MVC, adapte sua abordagem de revisão:

Para todos os Projetos (independentemente do status de refatoração):

  • Estrutura do Projeto: Verifique a visualização principal do repositório para garantir uma organização adequada
  • Remoção da funcionalidade de produtos: Verifique se a funcionalidade de produtos foi completamente removida
  • Navegação: Verifique se o cabeçalho/navegação não aponta para páginas inexistentes

Se o Projeto ainda não foi refatorado:

  • server.js: Revise as implementações de rotas e a configuração de middlewares
  • Diretório views/: Verifique a organização dos modelos EJS e das partials
  • Diretório public/: Verifique se os arquivos estáticos estão devidamente organizados

Se o Projeto iniciou/concluiu a refatoração do MVC:

  • src/controllers/: Revise a organização dos controllers e a separação de responsabilidades
  • src/models/: Verifique se os dados e a lógica de negócios estão devidamente separados
  • src/middleware/global.js: Verifique se o middleware consolidado está implementado corretamente
  • src/views/: Verifique a organização dos modelos
  • server.js: Deve estar limpo e focado apenas na configuração
  • Instruções de import/export: Verifique caminhos de arquivo corretos e padrões consistentes

3. Criar issues no GitHub

Quando encontrar problemas significativos, crie issues no GitHub. Veja como:

  1. Navegue até o arquivo com o problema
  2. Clique no número da linha onde ocorre o problema
  3. Clique nos três pontos (…) que aparecem
  4. Selecione "Reference in new issue"
  5. Escreva um título e uma descrição claros

4. Escrevendo boas issues no GitHub

Mantenha as issues do GitHub simples e úteis. Aqui estão exemplos de issues bem escritas para ambos os tipos de projetos:

Exemplo 1: Funcionalidade de produtos não removida


        Products route still exists after refactoring

        Found a products route that should have been removed as part of the MVC assignment cleanup:

        ```javascript
        app.get('/products', (req, res) => {
            // This entire route should be deleted
        });
        ```

        Please remove this route completely, along with:
        - Any products link in your navigation
        - The products.ejs template file if it exists
        - Any products-related variables or data

Exemplo 2: Problema de organização do MVC


        Controller contains data that should be in models

        The catalogPage controller is storing course data directly instead of using the model layer:

        ```javascript
        // This data should be moved to src/models/catalog/catalog.js
        const courses = { 'CS121': { title: 'Intro' } };
        ```

        Consider moving this data to your catalog model and importing it:
        ```javascript
        import { getAllCourses } from '../../models/catalog/catalog.js';
        const courses = getAllCourses();
        ```

Exemplo 3: Problema de qualidade de código tradicional


        Unused next parameter in catalog route

        The catalog route includes a `next` parameter but never uses it:

        ```javascript
        // Change this:
        app.get('/catalog', (req, res, next) => {
        
        // To this:
        app.get('/catalog', (req, res) => {
        ```

        This follows Express best practices and makes the code cleaner.

Exemplo 4: Problema no caminho de importação (Projetos MVC)


        Incorrect import path in routes.js

        The import statement for the catalog controller appears to have an incorrect path:

        ```javascript
        // Check if this path is correct
        import { catalogPage } from './catalog.js';
        ```

        Based on your directory structure, it should probably be:
        ```javascript
        import { catalogPage } from './catalog/catalog.js';
        ```

Crie 2 a 3 issues significativas por repositório revisado. Foque em issues que realmente melhorariam o código, quer estejam relacionadas à organização do MVC ou à qualidade geral do código.

Dedique o tempo necessário para fazer isso da maneira certa

A revisão de código não consiste apenas em encontrar problemas — trata-se de entender como o código funciona, aprender com diferentes abordagens e ajudar seus colegas de equipe a escrever softwares melhores. Cada issue criada deve ensinar algo valioso, seja para quem recebe o feedback ou para você como revisor. Esse processo aprimora sua capacidade de ler código criticamente, reconhecer padrões que levam a aplicações de fácil manutenção e comunicar conceitos técnicos com clareza. Lembre-se de que, no desenvolvimento profissional, a qualidade das suas revisões de código impacta diretamente a produtividade da equipe e a qualidade do código, portanto, desenvolver essa habilidade agora beneficiará toda a sua carreira.

Lista de verificação de revisão

Como você pode ter experiência limitada na realização de revisões de código, use esta lista de verificação abrangente como um guia para conduzir uma revisão minuciosa. Essas orientações detalhadas ajudarão você a identificar problemas que poderiam passar despercebidos e a desenvolver a abordagem sistemática que desenvolvedores profissionais usam. Marque apenas os itens que forem relevantes para o progresso atual de refatoração do seu colega de equipe:

Limpeza de funcionalidade (Todos os projetos)

  • Rotas de produtos completamente removidas do server.js ou dos controladores
  • Links de navegação de produtos removidos do header.ejs
  • Arquivos de modelo de produtos excluídos
  • Nenhum código de produtos comentado restante

Código tradicional do Express.js (se ainda não refatorado)

  • Manipuladores de rota usam parâmetros corretos (sem não utilizados next)
  • Middleware estático configurado: app.use(express.static('public'))
  • Parâmetros acessados via req.params e req.query
  • Modelos renderizados com res.render()
  • Tratamento de erros presente
  • Arquivos CSS em public/css/
  • Imagens em public/images/
  • Arquivos EJS em views/
  • Parciais em views/partials/

Arquitetura MVC (se a refatoração foi iniciada/concluída)

  • Controladores separados em arquivos lógicos em src/controllers/
  • Modelos contêm dados e lógica de negócios em src/models/
  • Middleware organizado em src/middleware/global.js
  • Função de middleware consolidada (não dividida desnecessariamente)
  • Visualizações movidas para src/views/
  • Arquivo de rotas importa corretamente controladores e middleware
  • Server.js focado em configuração, não em lógica de negócios
  • Instruções de importação/exportação usam caminhos de arquivo corretos
  • Controladores não contêm dados codificados diretamente (em vez disso, use modelos)
  • Manipulador de erros mostra informações diferentes em produção vs. desenvolvimento

Qualidade do código (Todos os projetos)

  • Nomes de variáveis são claros (não x, y, data)
  • Formatação e recuo consistentes
  • Sem código duplicado óbvio
  • Tratamento de erros adequado

Modelos EJS (Todos os projetos)

  • Sintaxe EJS correta (<%= %>, <%- include() %>)
  • Parciais incluídos corretamente
  • Variáveis usadas corretamente
  • Nenhum link quebrado ou referências a modelos ausentes

Você também praticou identificar quando as funcionalidades devem ser removidas durante a refatoração, o que é uma habilidade importante para manter bases de código limpas e objetivas à medida que os requisitos evoluem.
